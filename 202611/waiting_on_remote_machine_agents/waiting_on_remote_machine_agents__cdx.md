# Remote agent waits: owner-evaluated dependencies over the existing fleet transport

Independent research by **cdx**, 2026-11-07.

Remote waits are a useful addition to SASE. I recommend implementing them as durable launch dependencies whose completion is evaluated by the machine that owns the target. Reuse the existing enrolled-machine gateway and federation worker, but add a dedicated dependency contract. Do not decide completion from the fleet display feed, an SSH process check, or synchronized agent Markdown.

The requested `%wait:athena.foobar` can be supported as shorthand, with explicit disambiguation. I would make `%wait(foobar, machine=athena)` the canonical spelling. The larger design decisions concern identity, session completion, restart recovery, and unavailable machines; parsing the prefix is a small part of the work.

This report is based on independent inspection of SASE at `0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b` and the opened `sase-core` checkout at `317ea6a1252710e1d6c44d7289eb856f994950e0`, plus the external primary sources linked below. SASE's checked-in core pin was `c8adc878aedfda494731eb1c0a4ecbc359be1c0e`, so the linked checkout and CI pin are different snapshots. I did not inspect another swarm researcher's report or findings. I did not probe Athena, inspect private credentials, change enrollment, or run an end-to-end remote experiment. These are code-based findings and design recommendations, not a diagnosis of which live remote services are currently broken. An attempted lightweight Python parser probe could not import the workspace because the system interpreter lacked `pluggy`; no runtime parser result or passing test is claimed.

**What already exists is a substantial transport foundation, but not a remote dependency service.** The relevant pieces are:

| Area | Observed behavior | Consequence for this feature |
| --- | --- | --- |
| Machine enrollment | `sase machine init` is the canonical discovery/enrollment flow. It writes credentials and a machine record, activates configuration, then performs authenticated hello. Installation-identity changes require repair. | The user's understanding of `machine init` is correct. “Configured” should mean an enrolled, authorized installation, not merely a discovered hostname or a sibling-machine name. |
| Federation | A local Rust federation worker serves Python clients over IPC; it has bounded HTTP requests, shared concurrency limits, persisted read caching, per-host backoff, and pinned installation checks. | Extend this lane rather than introduce a separate SSH poller or network client in every waiter. |
| Local waits | A runner waits before starting its workflow. The scheduler normally writes `ready.json`; startup and a 60-second fallback can resolve dependencies independently. | Every release path must understand remote dependencies. Updating only the scheduler is unsafe. |
| Completion | Named waits require successful outcomes and understand sessions, gates, monitors, recovery successors, and epic following. | A row labeled DONE or a missing PID is not the required predicate. |
| Fleet reads | `/catalog`, `/batch`, and `/detail` return owner-projected UI data, including health and freshness. `/batch` uses the presentation snapshot. | Existing data is useful for selection and explanation, but is not a dependency-completion API. |
| Identity | Fleet contracts distinguish installation, project, logical agent/session, and exact instance. Aliases and display names are labels. | Bind the selected name to an owner-issued identity before waiting. |

Enrollment details are documented in [machine initialization](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/docs/reference/agents/machine-initialization.md) and the [remote dispatch runbook](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/docs/reference/integrations/remote-dispatch.md). The actual reusable controller boundary is [FederationFacade](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/src/sase/dispatch/federation/_facade.py), backed by [the worker's remote-host client](https://github.com/sase-org/sase-core/blob/317ea6a1252710e1d6c44d7289eb856f994950e0/crates/sase_gateway/src/federation_worker/imp/remote_hosts.rs). The small Python `FleetGatewayClient` mainly covers enrollment and hello; it is not the complete fleet read abstraction.

**Several details make a superficial implementation incorrect.**

First, `%wait` means successful dependency satisfaction, not simply terminal execution. Current named success outcomes include `completed`, `noop`, `epic_approved`, and `plan_committed`. Failure, kill, stop, malformed state, or missing evidence must not release a named waiter. `plan_rejected` has different treatment for exact identity waits. Gates and monitors carry distinct raw outcomes whose effective meaning depends on their shell state and follow-up. The existing [outcome normalization](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/src/sase/core/dismissed_agent_completion.py) and [candidate evaluation](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/src/sase/core/wait_dependency_resolution/_index_candidate_queries.py) should supply the semantic baseline.

Second, the default for a bare agent name is its session; `target=turn` captures the current turn at binding. Exact member references have their own effective-target rules. A provider returning or a gate becoming answered does not necessarily finish the session: a follow-up may still be starting. The current resolver even re-lists membership after reading completion markers to avoid releasing between predecessor completion and successor visibility. This is a real, tested race, not a hypothetical concern. See the Rust [target table](https://github.com/sase-org/sase-core/blob/317ea6a1252710e1d6c44d7289eb856f994950e0/crates/sase_core/src/wait_target.rs), Python [binding adapter](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/src/sase/agent/wait_target_binding.py), [confirmation algorithm](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/src/sase/core/wait_dependency_resolution/_confirmation.py), and [confirmation regression tests](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/tests/test_wait_dependency_release_confirmation.py).

Third, user-authored named waits default to following epics launched by their targets. `for_epic=false` opts out, and `target=turn` does not use that default. The shared release operation combines this with fresh membership confirmation. An owner endpoint that merely returns “session complete” would silently weaken `%wait` for planners. Remote epic-follow evidence must stay qualified by its owner and project; copying an Athena bead ID into Apollo's ordinary local bead-wait list would be wrong. See [the shared epic-follow release path](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/src/sase/core/wait_dependency_resolution/_epic_follow_release.py).

Fourth, a healthy HTTP response is not proof that the data is authoritative for release. The federation worker can return cached data after a transport failure or while backing off. The gateway also has snapshot freshness. Its presentation feed intentionally omits some records, including an age/count-bounded terminal window; explicit history scope removes that window but still applies presentation safety filters. `/batch` selects from the ordinary presentation snapshot. A target disappearing from that result can mean omission, pruning, or unavailability. See [gateway batch/detail reads](https://github.com/sase-org/sase-core/blob/317ea6a1252710e1d6c44d7289eb856f994950e0/crates/sase_gateway/src/fleet_reads/service.rs#L311) and [snapshot selection](https://github.com/sase-org/sase-core/blob/317ea6a1252710e1d6c44d7289eb856f994950e0/crates/sase_gateway/src/fleet_reads/snapshot.rs#L170). Even fetching every history page would not add the missing wait semantics.

Fifth, logical fleet IDs need a generation audit before they become wait handles. The wire types provide useful structure, but the current projection can fall back from an artifact ID to a name, and the session grouping helper can use the session label. A field named `agent_session_id` is not, by itself, proof that reuse of a human name creates a new immutable generation. Require an immutable root/run identity in every remote binding, including legacy records, or reject records that cannot be pinned safely. Sources: [fleet locators](https://github.com/sase-org/sase-core/blob/317ea6a1252710e1d6c44d7289eb856f994950e0/crates/sase_core/src/fleet_contract/locators.rs), [locator construction](https://github.com/sase-org/sase-core/blob/317ea6a1252710e1d6c44d7289eb856f994950e0/crates/sase_gateway/src/fleet_reads/resolution.rs#L171), and [session grouping](https://github.com/sase-org/sase-core/blob/317ea6a1252710e1d6c44d7289eb856f994950e0/crates/sase_core/src/fleet_agent_session.rs#L51).

Finally, there are two implementation traps outside the gateway. The typed launch planner has its own wait representation and can turn a name matching a sibling launch unit into a local logical dependency. Remote references must be structurally remote before that matching occurs. Separately, `wait_checks` has a two-second routine interval but a filesystem trigger watching local `.ace_refresh_pulse` files, with a 120-second quiet backstop. Remote completion alone does not touch that pulse. Sources: [typed wait resolution](https://github.com/sase-org/sase-core/blob/317ea6a1252710e1d6c44d7289eb856f994950e0/crates/sase_core/src/agent_launch/plan_resolution.rs), [launch wire types](https://github.com/sase-org/sase-core/blob/317ea6a1252710e1d6c44d7289eb856f994950e0/crates/sase_core/src/agent_launch/wires.rs#L537), [default scheduler configuration](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/src/sase/default_config.yml#L1469), and [runner barrier](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/src/sase/axe/run_agent_wait.py).

**The feature is worthwhile when its purpose is sequencing work across already trusted machines.** It lets Apollo launch a reviewer after an Athena implementation, or a synthesis agent after several remote researchers, without occupying a model while it polls. SASE already owns launch dependencies and remote identity, so this fits the product better than an unrelated orchestration system.

The cost is a new availability dependency. Once Apollo depends on Athena, Athena's gateway, credentials, retained completion records, and network path affect Apollo's progress. That cost is acceptable if waits explain their state and survive interruption. It is unacceptable if users see an unexplained WAITING forever, or if the system guesses success to escape an outage. The first release should prioritize correct diagnostics and recovery over low latency or broad selector support.

There is another boundary worth keeping explicit: **remote completion does not make remote outputs available locally**. An implementation may finish before its commit reaches the branch Apollo will fetch; a report may exist only in remote artifact storage. A dependent that needs those results should name the exact published revision or durable artifact and resolve it separately. Preserve whatever publication guarantees the owner's existing completion path already makes, but do not silently make `%wait` copy worktrees, pull arbitrary branches, import chats, or prove deployment readiness. For workflows whose true requirement is “this artifact/revision exists,” an artifact dependency may ultimately be a better abstraction than an agent dependency. That is a complementary future feature, not a reason to block this one.

**I would make the following requirement adjustments explicit.** All syntax and API names below are proposals, not currently supported features.

| Requirement | Recommended adjustment and reason |
| --- | --- |
| “Wait for agent to complete” | Preserve successful local wait semantics, including session handoffs and the current epic-follow policy. A future `on=terminal` mode should be separate and explicit. |
| Remote target | Initially support existing named agents/sessions and `target=turn` on directly enrolled installations. Defer remote clans, tribes, hoods, workflow groups, and arbitrary future names. This keeps binding deterministic. |
| Initial binding | A new wait must successfully resolve its target in a bounded owner request before it is accepted as a bound remote dependency. Missing, ambiguous, inaccessible, or unsupported targets produce actionable errors. Offline submission before binding is a separate future mode. |
| Name reuse | Pin the generation once. Follow only owner-proven continuations/recovery lineage allowed by the selected policy. A different later run with the same human name does not silently satisfy it. This intentionally differs from local latest-name recovery behavior. |
| Network loss after binding | Keep the dependency pending and retry. Distinguish unreachable, unauthorized, missing, quarantined, unsupported, and target failure. None means success. |
| Scope | Keep the waiter local. Do not lift the existing `%dispatch` plus `%wait` prohibition as part of this feature. Remote launch placement and remote dependency observation are separate changes. |
| Cancellation | Canceling Apollo's waiter cancels only the local wait. It does not stop Athena's producer. An explicit existing run-now action may bypass a dependency, but must record that bypass. |
| Outputs | Wait establishes ordering only; result retrieval and repository synchronization remain explicit. |
| Deadline | Preserve indefinite waits by default. An optional elapsed deadline should fail or block visibly, never convert uncertainty into success. `%wait(time=...)` already means a delay/floor, not a timeout. |

The dispatch combination restriction is explicit in the [current runbook](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/docs/reference/integrations/remote-dispatch.md). Keeping it avoids having to decide which controller's aliases, project context, or credentials a dispatched prompt should use.

**Use explicit machine selection as the stable grammar; treat dotted syntax as convenience.** Dots already occur in ordinary agent hoods and names. Existing owner normalization deliberately distinguishes explicit owner roots from arbitrary dotted strings, and dispatch aliases themselves may contain dots. A blind `split('.', 1)` would be incorrect. Sources: [identity snapshot and normalization](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/src/sase/core/agent_identity_facade.py) and [dispatch alias validation](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/src/sase/macro/_directive_values.py#L117).

The canonical examples should be:

```text
%wait(foobar, machine=athena)
%wait(foobar, machine=athena, target=turn)
%wait(foobar, machine=athena, for_epic=false)
%wait(athena.foobar, machine=local)
```

For `%wait:athena.foobar`, recognize a remote selector only against the enrolled alias registry. Require one unambiguous alias/name split and no conflicting local exact target; otherwise ask for the explicit form in an error. If aliases `a` and `a.b` both match `a.b.c`, report ambiguity instead of choosing a prefix by accident. With no enrolled alias match, retain ordinary local dotted-name behavior; document that explicit `machine=` is how users get immediate unknown-machine errors. Resolve this at new-launch normalization, persist the result, and never reinterpret old pending local waits when someone adds an alias. New enrollment can still affect the meaning of newly authored shorthand; that is why I would recommend the explicit form in documentation and generated prompts.

Resolve the target name on the owner, not by scanning the controller's displayed rows. If owner lookup finds multiple authorized projects/generations without a deterministic current target, return the candidates and require a project or exact locator. Do not assume Apollo's local project key equals Athena's key: the inspected gateway constructs its project locator from the owner's record. The resulting binding always includes the owner-issued project identity, even if the initial unique-name lookup did not require a project selector.

**The alternatives differ mainly in who is trusted to decide completion.**

| Approach | Merits | Problems | Verdict |
| --- | --- | --- | --- |
| SSH `sase agent wait` or marker polling | Quick diagnostic prototype; existing SSH access may help a human investigate. | Host-specific environments and paths, long process lifetimes, separate trust/configuration, per-wait connections, inconsistent lifecycle semantics. | Do not use as the product implementation. |
| Read the fleet catalog or `/batch` and inspect status | Reuses transport with little initial code. | Presentation filtering, stale snapshots, name reuse, missing session/epic release semantics. | Useful for selection and diagnostics only. |
| Re-import synchronized remote agents | Could resemble a local resolver input. | Recreates a second authority and a synchronization delay; the project has explicitly retired agent-import behavior. | Do not resurrect it for waits. |
| Add owner-evaluated dependency bind/check calls | Reuses enrollment and transport; places the predicate next to authoritative state; can batch and persist identity. | Requires a versioned contract and shared core predicate work. | Recommended. |
| Push callbacks or an event bus | Potentially lower latency. | Lost notifications, acknowledgments, replay, reverse connectivity, subscription lifecycle. Still needs authoritative reconciliation. | Later optimization, not the first correctness mechanism. |
| Adopt Temporal or another distributed workflow platform | Strong execution history and cross-worker coordination. | Large operational and product change relative to this request. | Borrow the identity/state ideas; do not adopt a platform just for this feature. |

The no-import direction comes from the project's supplied core decision record, “Agents-Sync Is Publish-Only, The Import Leg Is Deleted.” Historical machine-qualified transport helpers are not evidence that live remote wait support already exists.

**Implement one owner-side dependency evaluator and a durable controller binding.** A concrete design has these responsibilities:

| Component | Proposed responsibility |
| --- | --- |
| `sase_core` | Typed remote selector, target/policy validation, generation binding rules, shared completion predicate, observation validation, and release decisions. |
| Owner gateway | Authenticate a bounded bind/check request; gather authoritative owner facts; evaluate a target; return a small structured result without paths or credentials. |
| Federation worker | Route to the pinned installation; deduplicate and batch checks; enforce deadlines/concurrency/backoff; preserve transport and freshness diagnostics. |
| Apollo wait state | Persist the target, policy, waiter-spec revision, and accepted completion evidence; combine remote and local dependencies. |
| Scheduler and runner adapters | Call the shared decision path, arrange polling, and release only when all dependencies and time constraints are satisfied. |
| TUI/CLI/editor | Show the target and blocker clearly; generate and round-trip the same syntax. No network calls in rendering or completion callbacks. |

A suggested binding contains the requested display text, installation ID, owner project locator, immutable session-generation/root locator or exact instance locator, effective `session|turn` target, `for_epic` policy, protocol/predicate version, and a revision of the local wait specification. An alias is retained for display and connection lookup, but is not the identity. An endpoint change for the same installation may be recoverable; alias reassignment or machine repair to a different installation must not rebind an existing dependency silently.

Add small versioned operations such as `dependency_bind` and `dependency_check_batch` to federation IPC and owner gateway routes. These are proposed names. Binding resolves a human selector; subsequent checks take the pinned locator and policy. Both can be logically read-only: Apollo owns the durable wait, while Athena owns the target and its completion evidence. There is no need for Athena to launch a proxy agent or maintain a remote waiter process. Each batch item returns its own outcome so one malformed or unavailable target cannot discard healthy results.

Separate the result into binding status, dependency state, and observation health. For example, a valid pinned dependency may be `pending`, `satisfied`, or `blocked`, while its observation is `fresh`, `unreachable`, `unauthorized`, `identity_mismatch`, `unsupported`, or `gone`. Carry a structured reason, target identity, owner generation/revision, and observed time. Only an authoritative evaluation of the requested policy may assert satisfaction. HTTP 200, a display status, and a missing record never imply it.

Preserve session completion confirmation on the owner. The gateway must see pending finalizers and successor handoffs under the same rules as a local wait, and must verify membership after the resolving state read. Retain epic following by evaluating the owner's launched-epic evidence and closure state there. Persist any pinned follow evidence with the remote binding rather than translating it into unqualified local bead dependencies. Reuse the existing Rust epic-follow reducer where suitable, and include the waiter's canonical identity when evaluating known self/cycle cases.

This requires real core work. Much of today's wait aggregation still lives in Python under `core/wait_dependency_resolution/`; only portions such as the effective-target table and epic reducer are already Rust-owned. Do not implement a second simplified Rust predicate from display rows or a new Python remote-only predicate. Extract the needed pure session/generation/outcome rules into `sase_core`, put owner filesystem/index reads behind fact-gathering adapters, and make both local waits and the gateway consume the same semantics. It need not become a rewrite of every clan/tribe operation before the first remote agent wait, but the supported slice needs parity tests. Update PyO3 registration, wire mirrors, gateway route and contract declarations, compatibility fixtures, and SASE's core revision pin together.

**Persist successful evidence for a particular wait, not a reusable “this name is done” cache entry.** After Athena freshly confirms a bound dependency, Apollo should atomically save that evidence before publishing local readiness. Key it by pinned generation, selected policy, and the current waiter-spec revision. A later outage should not make that already-satisfied dependency unresolved again, including when Apollo is still waiting on another prerequisite or a time floor.

Conversely, an old cached DONE row from before binding is insufficient. A different wait created after someone resumes the session must re-evaluate the owner; it cannot inherit the earlier wait's satisfaction. Define the barrier precisely as successful owner-confirmed settlement at an observation cut for this binding. Later manually added work does not retroactively revoke a consumed barrier. Wall-clock timestamps are useful for display; use identity and revision fencing for correctness, and local monotonic time for request deadlines/backoff.

Retention is part of this contract. Exact dependency lookup must survive dismissal and removal from the presentation window. Use the owner's durable completion/archive evidence where it can establish the full predicate, and add a compact per-generation completion record if it cannot. Do not make full chats or all display rows permanent. Explicit loss/purge of required evidence returns `gone` and blocks; it never implies success. If retained evidence cannot support offline-controller recovery, that is a release blocker, not a reason to scrape the UI harder.

The same principle appears in Temporal's distinction between a workflow chain and individual runs: a continuation retains the workflow ID but obtains a new run ID, and result handles can explicitly follow runs. This is a useful analogy for SASE's session-versus-turn design, not a recommendation to introduce Temporal. See [Continue-As-New](https://docs.temporal.io/develop/go/workflows/continue-as-new) and [WorkflowHandle.result](https://python.temporal.io/temporalio.client.WorkflowHandle.html#result).

**Start with batched polling and add event acceleration only if measured latency needs it.** Poll only installations with outstanding remote dependencies, deduplicate identical targets/policies, and bound total work per host and per tick. A reasonable initial tuning hypothesis is a roughly five-second healthy poll interval with jitter and capped failure backoff; measure gateway cost and completion-to-release delay before making that a promise. Reuse the worker's existing request deadlines and per-host limits. Its inspected backoff is deterministic, so jitter must be deliberately added at one layer rather than assumed present. Avoid independent retry multiplication in the runner, scheduler, and HTTP client. The AWS [timeouts, retries, backoff, and jitter guidance](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) supports these operational choices.

For v1, use a separate periodic remote-dependency refresh job that writes accepted observations and touches the relevant local lifecycle pulse. `wait_checks` then evaluates local evidence without waiting for a slow host on every waiter. The initial bind and existing coarse runner fallback should use the same worker/service when the refresh job is absent. Requests from those paths need deduplication so many waiters do not independently hammer Athena. With no remote dependencies, incur no remote polling. Prove this works with the TUI closed and with no unrelated local lifecycle changes.

Audit every bypass and release entry point: startup, scheduler, fallback, refresh/relaunch restoration, wait edits, and kill/dismiss/run-now handling. Adding a new `remote_dependencies` field that an old resolver ignores can falsely release an otherwise empty local dependency set. Version persisted wait specifications, refuse unsupported kinds, invalidate completion evidence on edits, and fence ready publication against the same spec revision. Do not place remote filesystem paths into `wait_for_artifacts` to fit the old shape.

If event-driven wakeups are added later, use them as invalidations that trigger a check. A lost event must not strand a waiter. SASE already has a fleet events route; that may be reusable, but polling remains the reconciliation backstop. Kubernetes similarly requires clients to recover from expired watch history by re-reading state and restarting their watch. The applicable lesson is recoverable observation, not adopting Kubernetes. See [Kubernetes API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/#efficient-detection-of-changes).

**Keep authorization and compatibility narrow.** Require an enrolled pinned installation and a read capability sufficient for dependency evaluation. A dedicated dependency-read capability/scope is appropriate if returning settlement or archive evidence exceeds existing scopes; never require remote launch/stop permission merely to wait. Advertise the predicate version and supported target/policy combinations in hello. Old gateways should return an upgrade requirement, not fall back to name polling. Keep TLS validation, credentials, quarantine, and connection configuration in the existing fleet machinery. Enrollment must not happen implicitly from parsing a prompt.

Distributed dependency cycles remain possible: Apollo A can wait for Athena B while B waits for A. Reject cycles visible in a submitted plan, and report direct reciprocal dependencies when both owners expose evidence. Do not promise complete global cycle detection without a global graph. Deduplicated stalled-wait diagnostics should name the target, last successful observation, and reason; an explicit deadline/cancel/bypass gives the user a way out. None of these should automatically kill a producer or guess completion.

**Deliver this in verifiable slices.**

1. Freeze the semantic contract and fixtures: target identity/generation, success versus failure, session/turn behavior, epic following, alias ambiguity, name reuse, and outage states. Establish the shared core predicate for the supported slice before exposing the user syntax.
2. Add owner bind/check operations, history-safe exact lookup, capability negotiation, and federation IPC. Exercise them against a local test gateway with synthetic session lifecycles. A prototype may require explicit `for_epic=false`; do not silently make that the shipped default.
3. Add durable controller bindings, the remote refresh job, and common release evaluation across scheduler/startup/fallback. Ensure old markers cannot be reinterpreted and unknown dependency kinds cannot release.
4. Add explicit syntax, guarded dotted shorthand, launch preview, diagnostics, completions, and round-trip editing. Keep `%dispatch` combinations and remote group selectors out of scope.
5. Run a controlled Apollo-to-Athena pilot after both installations advertise the capability. Verify offline recovery and finalizer/handoff races before expanding the selector set or adding event streaming.

The acceptance suite should include:

| Scenario | Required behavior |
| --- | --- |
| Remote success, failure, kill, malformed marker, or missing target | Only the appropriate successful predicate releases; every other case has a specific blocker. |
| Gate answer, monitor completion, successor launch, finalizer delay | Session remains pending across the handoff window; a pinned turn follows its distinct target rules. |
| Planner launches an epic | Default wait includes the owner's epic completion; explicit opt-out releases at the chosen agent boundary. |
| Same name reused, alias renamed/reassigned, owner reinstalled | Binding remains on the original identity or blocks with a repair/rebind explanation. |
| Local dotted-name collision or dotted machine aliases | Deterministic parsing or an ambiguity error; explicit `machine=` always resolves intent. |
| Partial batch, stale cache, gateway restart, expired credentials | Healthy targets progress independently; uncertainty never becomes success. |
| Completion while Apollo is offline; target subsequently dismissed | Exact durable evidence permits recovery beyond display-feed retention. |
| Apollo crashes before/after saving satisfaction or writing readiness | Restart preserves the binding and accepted evidence; no duplicate logical release or unsafe bypass. |
| Wait edited while an HTTP response is in flight | Old spec revision cannot satisfy the edited dependency. |
| Scheduler job absent; TUI closed; no local pulse | Coarse fallback still progresses; normal operation uses the intended remote polling cadence. |
| Mixed local/remote prerequisites plus `time=` | All predicates compose; already accepted remote success survives a later outage; existing delay semantics remain intact. |
| Many waiters share one target; one host hangs | Checks deduplicate and remain bounded; local and unrelated remote waits continue. |
| Old gateway or old stored schema | Explicit unsupported-version behavior; no interpretation of absent fields as success. |

Existing tests for [gate follow-up windows](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/tests/test_gate_wait_dependency_pending_followup.py), [wait target grammar](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/tests/test_directives_wait_target.py), and [fleet gateway behavior](https://github.com/sase-org/sase/blob/0ba9cfc9f1ac2696cb6faeed515cd98483bcac3b/tests/dispatch/test_machine_bootstrap_real_gateway.py) provide useful starting fixtures. They were inspected as source, not executed in this research turn.

The main remaining implementation uncertainty is how much of the owner-side wait fact collection can be shared with the Rust gateway without expanding the migration unnecessarily. The existing fleet locator generation and archive sufficiency also need explicit validation before they become stable remote handles. These uncertainties argue for the first two slices above; they do not justify rebuilding all remote support first.

**Recommended solution:** implement existing-agent remote waits as a narrow extension of SASE's dependency system: explicit machine selection with safe `%wait:athena.foobar` shorthand, owner-issued generation-pinned bindings, owner-evaluated completion through a shared Rust predicate, and durable satisfaction evidence on Apollo. Carry the checks over the existing authenticated federation worker, refresh them with bounded batched polling, and integrate every local release path. Preserve successful session/turn and epic-follow semantics, keep unavailable machines visibly pending, and leave output transfer, remote group selectors, and `%dispatch` composition for separate work. This provides the requested capability without making display caches or network liveness responsible for correctness.
