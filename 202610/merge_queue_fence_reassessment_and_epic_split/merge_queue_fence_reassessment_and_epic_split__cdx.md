# Reassessing merge-queue admission and exact-SHA releases: revised requirements and four independently verifiable epics

Independent research by **cdx**, 2026-10-17.

**Recommendation.** Keep the architectural direction: qualify and publish a fixed release candidate, and use GitHub's native merge queue to enforce integration checks before ordinary changes reach `sase`'s `master`. Implement it as **four epics**, with explicit acceptance contracts:

1. Exact-candidate release qualification and publication.
2. Trustworthy, event-correct integration checks.
3. Durable asynchronous landing and completion.
4. Production enforcement, migration, and operational acceptance.

The first two can deliver independently. The third can be proved in a scratch repository without changing production protections. The fourth consumes their evidence and proves that the deployed system actually enforces the policy across writers and machines. Release safety should ship before queue enforcement; a release should not wait for the completion-state migration.

This is a reassessment of the shared [original proposal](merge_queue_fenced_master_and_exact_sha_releases/merge_queue_fenced_master_and_exact_sha_releases.md), not an implementation plan or a set of newly created beads. I did not inspect any other researcher's report, transcript, summary, or findings from the current swarm. The original consolidated proposal is shared input; its historical measurements are treated as reported evidence, not as measurements I reproduced.

**What survives reassessment.** PRs are suitable admission records, zero required reviews fit this workflow, integration testing belongs on the server, and merge commits preserve useful commit provenance. Full release qualification should remain separate from the bounded merge gate. Host-owned completion should remain host-owned. The proposed distinction between a completed agent turn and a completed landing is essential.

**What changes most.** The proposal overstates what tests can guarantee, has a contradictory PR-admission aggregate, underspecifies release retry identity and multi-repository completion, and treats capacity and flake estimates as firmer than their evidence supports. Its “cheap Phase 0” includes a release protocol, not merely a checkout edit. Production enforcement also needs its own observable finish line.

**Evidence and limits.** I read the original through `sase artifact read`, opened linked/external repositories through `sase repo open`, inspected local source, queried GitHub read-only APIs, checked the PyPI JSON API, and consulted current official GitHub/PyPI documentation. I made no workflow, ruleset, release, application, or runtime configuration changes and ran no CI experiment. In particular, no scratch queue was created and no PyPI upload was attempted.

**Explicit requirement changes.** The following are proposed replacements or additions, not silent interpretations of the original.

| ID | Original requirement or assumption | Revised requirement and reason |
| --- | --- | --- |
| R1 — narrow the guarantee | “Zero deterministic failures admitted”; a red local check means the agent broke it | Every ordinary landing must carry successful evidence for the declared integration policy on its integrated candidate. No test suite proves absence of all deterministic defects; local configuration, dependencies, and untested paths can still fail. Keep failure triage and independent witnesses. |
| R2 — correct release identity | Build whatever master is “when the job runs”; then add one `ref` | Default checkout is tied to workflow event context, not necessarily live master at job start. The defect is failure to bind build and qualification to the release SHA. Resolve one immutable candidate and thread it through **every** checkout, nested workflow, package build, and evidence record. |
| R3 — define retries and artifacts | Build once, explicit tag retry, skip files already uploaded | Treat candidate version, peeled tag commit, source tree, qualification policy, run attempts, and artifact digests as a bound record. Resume with the original qualified files; verify remote digests before accepting an existing filename. Refuse mismatches. A fresh rebuild is a new build needing qualification, even at the same source SHA. |
| R4 — remove contradictory admission semantics | Skip expensive PR jobs, while `integration-ready` requires every dependency to succeed | Specify event-dependent expected jobs explicitly, or initially run the real fast suite on both PR and merge-group events. A cheap PR pass is only admission eligibility; it must never be accepted as integrated verification. Missing/skipped mandatory merge-group jobs fail closed. |
| R5 — make release coverage explicit | Everything that can block a release should block merges, except with owner/deadline; immediately add visual CI | Retain two tiers with a versioned check inventory. Promote checks into the merge gate after measuring runtime, flakiness, and marginal detection value. Expensive release-only checks have owners, response times, and a repair policy. Do not require moving the entire visual lane into the fast gate as a prerequisite. |
| R6 — tighten flake treatment | Retry up to three failed nodes; quarantine; infer <3% false reds from annotations | A pass in isolation does not disprove an order-dependent regression. Retry only under an explicit evidence-backed policy with bounded budget and retained first-attempt results. Unknown failures block. Track raw failures, recovered attempts, residual spurious rejections, and unknowns separately. Quarantine requires independent evidence, owner, expiry, and continued execution. |
| R7 — defer cadence/capacity changes to measurement | Concurrency 2 is shown to fit; nightly Full CI frees about ten slots | Treat concurrency 2 as a starting hypothesis. Re-measure the actual post-change DAG, including PR checks, merge-group checks, push audits, retries, visual work, core cache misses, and release qualification. Coordinate both GitHub schedules and `ci_watch` dispatch/freshness settings. |
| R8 — correct merge proof | Compare current master's tree with the tested queue tree; look up by SHA | Prove a mapping from PR/head to successful merge-group run to the specific resulting base update. | R9 — expand the landing protocol | `queued → merged/ejected/superseded`; finalizer must prove queued before ending | Persist intent before network effects; represent submission uncertainty, waiting for admission/auto-merge, queue membership, proof pending, and completion effects. | R10 — scope completion correctly | Never close any bead without proof of merge | Defer **code-delivery** completion and its dependents until all declared landing obligations are verified. Keep production enforcement open until its contract actually passes. |

R1 does not weaken admission: a failed required check still blocks. It removes an unprovable promise. R5 similarly preserves full release qualification; it prevents the merge gate from silently becoming the 100-minute lane that the proposal otherwise rejects.

**Release design that satisfies R2–R3.** Distinguish three identities: workflow implementation revision, candidate source commit, and uploaded distribution files. They can legitimately differ in representation; they must be bound explicitly rather than inferred from `github.sha`.

The candidate resolver should produce at least repository, version, tag, peeled commit SHA, tree ID, core source pin, and qualification policy version. Qualification records additionally identify workflow run IDs/attempts, executed jobs, actual checkout SHAs, dependency versions and artifact SHA-256 digests. Missing release outputs are an error when publication was requested. Propagate the outputs from whichever release-please retry actually produced the release; a later successful no-op must not invent a candidate.

GitHub defines scheduled runs using the default-branch event SHA and merge-group runs using the merge-group SHA. Reusable workflows retain the caller's GitHub context. Passing `ref` to a top-level job does not magically retarget nested checkouts or turn a caller's `headSha` into a proof of the candidate. Inspect `build-core.yml`, local composite actions and every source-consuming job, and emit the resolved source SHA from each. Use candidate-scoped concurrency so nightly CI cannot cancel a release qualification sharing `refs/heads/master`. [Workflow event identities](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [reusable workflow context](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations).

Build wheel and sdist once for the candidate. Run source qualification on that candidate and package/install smokes against the built files, including published core floor and normal dependency resolution. Smoke installation from the sdist also checks that the second published distribution is usable. This is a precise version of “publish what was tested”: it does not pretend every source test ran out of the wheel. Retain the qualified artifact set for interrupted uploads. Verify digests before and after publication; `skip-existing` by itself is not equality proof. PyPI attestations can preserve publisher/digest provenance, but they do not substitute for test evidence. [PyPI attestations](https://docs.pypi.org/attestations/).

Model `candidate prepared`, `qualifying`, `qualification failed`, `qualified`, `publishing/partial`, and `published and confirmed` distinctly. A GitHub tag or release is not proof of a usable PyPI version. A failed candidate remains unpublished; a fix produces a new candidate. Never move a release tag to turn failed qualification green. An explicit retry names the old tag/candidate and either resumes its qualified bytes or requalifies new bytes. If the old artifacts have expired, report that fact rather than silently rebuilding and mixing files from different attempts.

The initial implementation can retain release-please and allow a GitHub release/tag before PyPI publication, with honest state reporting. Separating tag creation or using drafts is optional until its recovery semantics are tested. Migrating to hatch-vcs is a separate product decision, not an escape hatch from Full CI.

Before relaxing the six-hour heavy-green pre-merge condition, deploy the new publisher's mandatory exact-candidate check. Otherwise the migration creates a window in which the old broad publisher can publish without either protection. Keep publication credentials isolated from candidate test execution. Production recovery should verify the version and downloaded digests from PyPI and run a clean install, rather than conclude success from a release API response.

**Integration gate design that satisfies R4–R7.** GitHub requires merge-group checks to be triggered explicitly. Its queue build concurrency counts merge groups, while merge limits control how many already-qualified PRs are merged together; increasing a merge limit does not batch several builds into one. Use merge commits initially, keep non-failing-PR enforcement enabled, and treat concurrency 1 versus 2 as a measured choice. The cited April incident is not necessary to justify this choice, and I did not re-investigate that historical incident. [GitHub merge queue documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue).

The required aggregate needs a contract for each event. For a first safe implementation, run the same fast integration policy on PR and merge-group events. If the measured duplicate work is excessive, introduce cheap PR eligibility explicitly. That variant must have an event-aware aggregate that verifies the intended PR checks, while requiring **all** integration jobs for `merge_group`. It must not be implemented as “accept skipped jobs everywhere.” There must always be a non-skipped aggregate that examines expected jobs and results; unexpected empty collections, failed setup, cancellation, timeouts, and skipped mandatory jobs cannot produce admission success. GitHub permits skipped jobs to satisfy required-check semantics, so this logic needs negative tests, not merely a YAML trigger assertion. [Required-check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

For release compatibility checks, do not use the PR branch name as the sole applicability test: a merge-group ref is not the release-please branch. The full candidate pipeline always runs the core-floor checks. If a core-floor check becomes a required merge check, its applicability must be defined on both events without leaving unmatched required contexts pending.

I would keep today's scheduled heavy cadence during initial gate repair, then decide whether nightly coverage is acceptable after candidate qualification is reliable. The source already records a roughly 30-minute visual first pass, versus the original fast-gate median around 13 minutes. Sharding might reduce wall time, but increases runner demand. Neither “it is sharded” nor changing a cron establishes free capacity. Also update the configured two-hour `ci_watch` dispatcher and six-hour freshness rule if nightly becomes policy.

`if: always()` belongs on reporting and the aggregate. Apply it to other steps selectively: a formatting or lint failure may justify continuing independent diagnostics; a failed environment installation does not make dependent test execution meaningful.

For flakes, retain an auditable first failure and rerun outcome. A same-SHA pass is useful evidence, but an isolated-node pass can conceal a deterministic interaction caused by test order. An allowlisted retry may recover a witnessed infrastructure or known flake failure; novel signatures and harness/collection errors remain blocking. A repaired commit is a new attempt, not a successful retry of the old SHA. Quarantine must not remove release-critical functionality from all qualification; document how its risk is covered and keep the quarantined job visible.

The original 30–40% false-red estimate is a hypothesis based on failure shapes. A change not touching a failed test is not sufficient proof of a flake. The proposed `<3%` target can remain an operational objective, but report its numerator, denominator, adjudication method and uncertainty. `FLAKY:` annotation frequency measures recovered failures, not residual false rejections. Preserve unknowns; do not improve the metric by relabeling them. As a statistical sanity check, zero observed events in 100 comparable independent trials yields an approximately 3% one-sided 95% upper bound; clustering across shared infrastructure can make even that optimistic.

**Landing design that satisfies R8–R11.** Successful `gh pr merge` can enable auto-merge or enter a queue; it is not evidence that a merge occurred. The CLI documentation says so directly. The current plugin's success path is therefore incompatible with queue activation. [GitHub CLI merge semantics](https://cli.github.com/manual/gh_pr_merge).

A minimum durable record identifies the repository/base branch, host finalizer declaration and repository obligation, stable operation ID, source head SHA, PR, requested bead action, and dependency obligations. It records submission attempts and uncertain outcomes before retrying them. Suggested states include prepared, submitting, waiting for admission, queued, merged pending proof, landed, retryable rejection, and terminal cancellation/supersession. Names are implementation choices; preserving these distinctions is the requirement.

Use the Rust core for state transitions and wire contracts, the GitHub plugin for provider operations, and thin host/Python adapters for execution. Reuse the existing finalizer declaration and independent verification boundary. Do not make an LLM decide whether a merge succeeded. Reconciliation should use GitHub as the authoritative remote merge source and an idempotent local/durable journal for completion effects. Two hosts may observe the same PR; both must converge without duplicate repair launches or completion effects. A per-host lock is insufficient for this obligation.

Record an intent before creating a branch/PR. After a network timeout, search by the operation identity before creating another. Preserve the branch/commit durably before freeing the original workspace. A queued rejection must remain repairable after that workspace has been reused. Store enough failure evidence to classify removal without relying on a transient queue ref remaining available. Do not delete rejected source branches as though they merged.

The proof chain is:

`source head → PR revision → merge-group candidate/run/attempt → resulting base update → declared completion effects`

For merge commits, prove source-head ancestry in the appropriate resulting base update. Compare the relevant historical tree with the successful integrated candidate, accounting for group membership. Comparing current master is wrong once later changes have landed. A group can cover several PRs; individual PR merge SHAs and the group's resulting base update may not be interchangeable. Retain the push audit until the pilot demonstrates the real mapping. Tree equality alone does not prove equivalence for tests dependent on commit history, event context, secrets or workflow version. Where the mapping cannot be proved, withhold delivery completion and obtain actual post-merge verification; do not guess.

SHA-only lookup is consequently insufficient. Evidence queries need repository, workflow identity/policy, event, expected candidate, run attempt and conclusion. A cheap PR eligibility success, unrelated workflow, old attempt, or another SHA must never qualify a landing or release. Use positive evidence selection, not “most recently green workflow with this display name.”

Defer a requested code-delivery `close` action until the declared required repositories have landed. Preserve `keep`. Research-only work, canceled tasks and superseded work must retain their own completion semantics; the blanket “never close any bead without merge” would break them. Do not conflate this with closing a human-owned goal. Dependency waiters must consume verified delivery, not merely absence of a running agent.

For a declaration changing core and Python callers, land the necessary core work, update the source pin to an accepted reachable core revision, and then land the dependent Python change. The wheel used for source CI and the minimum core distribution available on PyPI are different proofs. A green source-pinned build cannot compensate for an unpublished runtime floor. Support mixed direct/queued repository obligations during migration, without recursively queueing SDD bookkeeping needed to record that a landing finished.

Bound retry and repair budgets durably per operation/revision, across machine restarts. A new pushed head invalidates old candidate proof and must match the submission guard. Explicit ejection, lost credentials, rate limiting, ambiguous API state, and a closed-unmerged PR must not all become “repair code.” Add automatic LLM repair only after deterministic reconciliation and bounded deduplication are proven.

**Why four epics rather than one.** Each boundary owns a different observable invariant and can be accepted with distinct evidence. A single epic would couple immediate release correctness to a cross-repository completion migration and a week of operational observation. It could report broad progress while none of its safety promises was independently closed. Conversely, making every YAML edit, retry helper, or ruleset toggle a separate epic would fragment end-to-end ownership.

| Epic | Deliverable / acceptance unit | Prerequisites | Value if subsequent epics stop |
| --- | --- | --- | --- |
| E1: exact-candidate release | Qualified artifact set is the only publishable set | None of E2–E4; specific existing CI defects may need repair for a successful production candidate | Correct releases and safe recovery under the current landing model |
| E2: trustworthy integration gate | One explicit policy reports truthful results on supported events | None of E1/E3; coordinate shared workflow interfaces with E1 | Better CI evidence, lower false rejection, usable admission checks |
| E3: durable queue landing | Submission, remote merge and completion are independently modeled and reconciled | Can use a small fixture gate; E2 needed for realistic production integration | Correct asynchronous `gh` submission and recoverable optional queue mode |
| E4: enforced production operation | All in-scope writers obey the deployed fence; delivery and release observability remain correct | E2 and E3 complete; E1 complete for this program's release outcome | The requested production policy is actually enforced and operationally proven |

E4 is a real rollout epic, not a placeholder for one settings change: it owns writer migration, cross-host recovery rehearsal, effective-rule verification, token/event behavior, a measured pilot and production acceptance. If the project strongly prefers fewer epics, combining **E3 and E4** is defensible only if that combined epic remains open through enforcement and soak. Do not merge E1 into it, and do not call a flagged queue implementation “master fenced.” My preferred recommendation remains four.

**E1 — exact-candidate release qualification and publication.** Own the candidate resolver, `publish.yml`, nested qualification inputs, artifact retention/digests, explicit tag retry, watcher release-state migration, and core-floor/install proof. Keep versioning on release-please. Do not make queue adoption, automatic repair agents or a broad unrelated CI cleanup prerequisites. Shared backend logic, if introduced, follows the Rust boundary; workflow-specific orchestration need not become a general release platform.

Independent verification:

1. In a controlled workflow fixture, select release commit A, advance master to B before qualification/build, and prove every source-consuming job reports A. Repeat with a nested core build whose pin differs between A and B. Assert that an empty SHA or a tag/version mismatch blocks.
2. Exercise release-please success on each retry position and an explicit existing-tag retry. Confirm they resolve the same candidate tuple. A no-release run performs no publication.
3. Fail each required qualification class in turn—supported Python version, visual/performance policy, core floor and package smoke—and prove the publish job is not eligible. Include skipped/canceled jobs, not just assertion failures.
4. Run nightly qualification and release qualification concurrently for different candidates. Prove they do not cancel each other or exchange artifacts. Document recovery for interrupted or replaced pending jobs. GitHub concurrency groups can replace pending work even when in-progress cancellation is disabled; explicit queue behavior is separate. [Concurrency documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).
5. Use a test publisher/scratch registry to interrupt after one file. Resume with the identical artifact set; accept an existing identical file, reject an existing filename with a different digest. Test missing retained artifacts and two concurrent retry requests.
6. Complete a green candidate on the current landing model and verify downstream downloaded digests, version, clean wheel/sdist install, and published core dependencies. TestPyPI or a fixture proves protocol behavior; an authorized production release proves the actual Trusted Publisher/environment configuration. Do not label the latter verified if it was not exercised.
7. Demonstrate an honest qualification-failed state and safe fix-forward candidate without retagging. Confirm that a GitHub release alone never marks PyPI delivery complete.

Evidence retained at acceptance: one successful candidate record with downloaded artifact hashes, negative-path workflow records, retry/partial-upload transcript, and the precise production capability actually exercised. E1 can be protocol-complete while an unrelated product regression blocks a candidate; report that limitation explicitly rather than claiming releases resumed.

**E2 — trustworthy integration checks.** Own the policy inventory, aggregate/event behavior, retry/quarantine semantics, targeted deterministic test repairs, and capacity measurements for the selected gate. Keep the heavy lane until its replacement dispatch/freshness policy is deliberately deployed. Provide one documented candidate/evidence interface to E3/E4. Do not make a seven-day wait the only implementation verification.

Independent verification:

1. Run a CI fixture matrix for PR, merge-group, master push audit, scheduled heavy and candidate qualification. Assert the expected job set and actual checked-out SHA for each event.
2. Inject failure, cancellation, setup error, timeout, missing matrix shard, skipped mandatory job, and zero-test collection. The aggregate must fail or stay non-successful. An intentional non-applicable job is accepted only where its event contract permits it.
3. Demonstrate that ordinary PRs, release-please PRs and ratchet PRs all produce required contexts; merge-group behavior must not depend on PR branch names being present. If cheap admission is chosen, show that its success cannot satisfy integrated evidence consumption.
4. Use a deterministic failing test, a controlled intermittent test, an order-dependent failure and a collection/harness error to test retries. Deterministic/unknown/order-dependent failures must not be silently converted to green by isolated reruns. Preserve raw results and cap attempt budgets.
5. Test quarantine expiry, duplicate/invalid entries, and continued execution. An expired entry fails the policy check. A failure cannot disappear from both admission and release coverage without an explicit policy decision.
6. Replay or sample the actual gate with warm and cold core caches and competing heavy/release jobs. Measure queue wait, wall time, runner-minutes and builds per delivered PR. Compare concurrency 1 and 2 before declaring either adequate.
7. Report an observation window and sample size for raw failure/recovery/residual rejection rates, with unknowns retained. The original p50 <30m, p95 <60m and <3% confirmed false rejection targets remain provisional acceptance objectives; changes require explicit justification rather than retroactively redefining the metric.

Evidence retained: event/job contract, negative-test results, first/retry failure records, quarantine audit, and measurements for the chosen DAG. E2 can be accepted before production protections require it.

**E3 — durable asynchronous landing and completion.** Own the Rust state/wire model, GitHub adapter, finalizer submission and verification integration, delayed code-delivery effects, cross-repository dependency handling, and a deterministic reconciler. Include the current `_submit_via_pr_merge` correction. A feature-controlled opt-in mode is suitable; production enforcement belongs to E4. Compatibility must include non-GitHub/direct paths where still configured.

Independent verification:

1. On an approved scratch repository, submit a change whose required checks are pending. Let `gh pr merge` return successfully. Prove the turn can end with a durable obligation while Patch delivery, requested code-bead closure and dependent phases remain unresolved.
2. Inject crashes/timeouts immediately before and after branch creation, PR creation, admission, remote merge, proof persistence and completion effects. Restart and show one logical PR/landing, no lost change and no duplicate closure or repair launch.
3. Run reconcilers on two hosts against the same operation, then terminate the originating host and recycle its workspace. The surviving host must reconstruct the obligation and complete or diagnose it from durable evidence.
4. Prove a normal successful merge, a two-PR group, and another master update before reconciliation. Source ancestry and the historical base-update mapping must verify without comparing against the later tip. If SHA identity differs, exercise the documented fallback proof rather than assuming equivalence.
5. Change the PR head after admission, eject it, close it unmerged, supersede it, and return ambiguous/transient API responses. Old proof must never qualify a new head, and no unmerged case may release a dependent code phase.
6. Test a declaration touching core, the main repo and a bookkeeping sidecar. The dependent main change waits for the correct core landing; the pin is correct; `keep` remains open; sidecar completion does not form a queue cycle. A required sibling failure prevents overall delivery success.
7. Exercise actual binding round trips and pin the new Rust implementation before Python consumers use it. Run the repositories' prescribed checks; targeted fixtures do not substitute for their required verification gates.
8. Verify bounded retry counts across restart and deliberate cancellation without lost source branches. Automated repair must not push or merge an unexpected head or bypass server checks.

Evidence retained: immutable operation histories, scratch PR/check/base-update references, restart/two-host traces, and domain/binding/adapter test results. E3 is complete when optional queue mode is correct and recoverable; production master can still be unenforced at this point, stated plainly.

**E4 — production enforcement and operational acceptance.** Own the deployed writer inventory and policy configuration, credential/event behavior, pilot and cutover, migration of every evidence consumer, incident procedures and observation. This epic closes the user-visible promise. It must not finish merely because a ruleset API call succeeded.

Independent verification:

1. Enumerate all writers to `sase` master: root and repair finalizers on both hosts, plugin PR submission, release-please/`ci_watch`, maintenance ratchets, and human CLI/web paths. Record the credential and route for each. Test real workflow triggering with those identities; do not infer it from token names. GitHub documents distinct `GITHUB_TOKEN` behavior, including approval-required PR workflows in current documentation, while App/PAT flows can run automatically. [Workflow triggering](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).
2. On a scratch repository with equivalent settings, prove a failing candidate cannot advance the base; two changes passing independently but failing together cannot land together; direct push is rejected with ordinary agent credentials; force push and deletion are rejected; missing/forged-by-wrong-producer checks cannot satisfy the required context.
3. Complete the limited production pilot, retaining a separately named push audit and keeping its evidence distinct from admission checks. Include ordinary, release and ratchet PRs and traffic from both hosts. Record the effects of remaining direct pushes on queue churn; an unenforced pilot is not proof of a fenced branch.
4. Export and verify effective production rules: exact target `master`, PR requirement with zero reviews, required merge queue, unique required aggregate with expected producer, merge method, no ordinary bypass, and force-push/deletion denial. Keep safety rules separately controllable from queue availability. [Ruleset layering and control](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).
5. Verify the production policy after activation, using safe canaries and remote read-back. Confirm every delivery has the landing/evidence link and every code phase waits for it. Test host restart during real pending work. Compare actual behavior with the pre-cutover baseline.
6. Migrate `release_watch` and the actual `ci_watch` implementation/configuration before retiring push evidence. Handle absent/stale/malformed records visibly. If nightly is selected, verify both cron and stale-run dispatcher behavior over a full interval. Define one owner for failure notifications; introducing repair launching is an explicit new responsibility, not an undocumented change to `ci_watch`.
7. Run an exact-candidate release through the new landing path and verify E1's production evidence. A main-branch qualification failure must not be bypassed because the merge queue passed.
8. Observe at least seven days **and a declared adequate sample**, with the chosen latency/capacity objectives, no unexplained delivery-proof gaps, bounded repair behavior and no silent fallback. Low traffic extends observation. Retain the push audit until complete mapping and consumer behavior are demonstrated, then remove its expensive work without removing lightweight provenance checks.
9. Rehearse a queue/API outage: persist outstanding obligations, stop automatic admission if necessary, preserve completed release artifacts, and recover without duplicates. Ordinary rollback keeps protection. A human emergency override records the affected commits and requires post-event verification; the system never treats disabled enforcement as a green queue result.

Evidence retained: effective-rule exports before/after, writer/credential matrix, safe rejection proofs, cross-host traces, one complete release provenance chain, pilot/soak metrics and the exercised incident procedure. This epic remains open if enforcement or the production soak cannot be demonstrated.

**Sequencing and interfaces.** Begin E1 and E2 independently, agreeing early on `candidate_sha` and qualification evidence schemas because both touch `ci.yml` and `build-core.yml`. E3 can proceed with a fixture policy while those contracts stabilize. E4 preparation can inventory writers early, but production cutover waits for E2/E3, and program-level release acceptance waits for E1. Assign one owner for shared workflow edits to avoid incompatible checkout/concurrency changes. Do not make later epics “verify the previous one”; each predecessor retains its own acceptance evidence.

A release safety failure pauses publishing, not all development. An integration-policy failure blocks the affected merge. A reconciliation uncertainty withholds delivery completion while preserving the work. A queue outage pauses admission without erasing the fence. Those separate failure boundaries are the main justification for the epic split.

**Remaining decisions to resolve through the epics.** Actual queue SHA/base-update correspondence; trustworthy retention of group evidence after temporary refs disappear; the installed `ci_watch` implementation's owner; the chosen retry policy; whether visual coverage belongs in the initial integration budget; and the performance of concurrency 1 versus 2 under the new DAG all remain empirical questions. They are bounded verification tasks with explicit outcomes, not reasons to postpone exact-release safety.

The recommendation revisits the queue portion of `decisions:ci-two-speed-split`, while preserving two-speed verification and `decisions:host-owned-completion`. It does not authorize memory edits, deploy a flag, create epics or change protections. The implementation should reconcile those decision records through the project's prescribed memory workflow once the revised policy is approved. Local agent verification remains `just check` through the prescribed SASE tool wrapper; this research does not authorize blanket agent runs of `just check-full`.

**Acceptance standard.** The program succeeds when ordinary `sase` master updates have attributable integrated-check evidence, host completion waits for the right delivery obligations, and published files are exactly the qualified candidate's files. Release cadence and landing latency are measured service objectives layered on those proofs. Four epics make those outcomes independently reviewable and prevent a slow queue migration from holding the release fix hostage.
