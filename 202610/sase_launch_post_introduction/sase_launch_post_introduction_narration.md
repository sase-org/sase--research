## The proposed introduction

Here is the proposed introduction, in Bryan's voice.

I've always been proud to call myself a Software Engineer. It's always been an easy thing to take pride in. The dolla dolla bills didn't hurt. I could tell you that I started working on sase because of the obvious need for structure I saw at Google. Or because I saw an opportunity to add some value. But the truth is, maybe it was just my pride. Building sase is my attempt to take back some control. This thing seemed like it was coming for a core part of my identity.

A year ago, sase was a 98-line LangGraph script in my dotfiles. Its only tools were a fake weather lookup and a calculator. Today its repo holds 15,756 commits and over 2 million lines of Python. More than half of it is tests. Since July, 19 out of every 20 commits have been signed by the coding agent that wrote them. That's a lot of motion. But, to paraphrase OpenAI's Akshay Nathan, motion isn't progress. Well, I've tried. I've tried a lot. I've kept trying because I'm still not quite sure what I want, even after all this time. That frustrates me.

This post is about the parts that stuck. Together they make up sase, Structured Agentic Software Engineering, pronounced sassy. It's an open-source layer around the coding-agent command-line interfaces you may already use, like Claude Code and Codex. It runs them in isolated workspaces and keeps a durable record of what each one did. One developer supervises all of it from a single keyboard-driven terminal user interface. If you already juggle more than one coding agent at a time, this post is for you. It covers how I got here, what sase generalizes, and what all that motion cost. If you'd rather just try it, start with Getting Started.
