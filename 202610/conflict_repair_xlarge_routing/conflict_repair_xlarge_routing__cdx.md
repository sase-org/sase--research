**Route finalizer conflict repair through @xlarge: implementation research and critique**

Independent report by researcher **cdx**, 2026-10-27. No other report, transcript, or findings from this research swarm were consulted. This is research and a proposed design; no application code was changed.

**The proposal is a good default, with a narrower and more precise contract.** When the built-in commit finalizer has exhausted its existing deterministic handling and is about to spend its permitted model turn resolving a paused merge/rebase, select that turn through `@xlarge`. Do this on the first such turn. Keep the existing repair bounds, checkpoint/resume rules, and verification obligations. The change should select the complete provider/model/effort tuple; changing the model string alone is insufficient.

I would describe this as a **conflict-repair routing policy**, rather than promise an intelligence upgrade. An alias can select the same model, a different provider, or a user-overridden target. I recommend one explicit configuration escape hatch for operators, plus evidence showing what actually executed. There is no measured SASE-specific quality or cost result in this investigation that establishes an unconditional benefit for every conflict.

**Evidence and scope.** I inspected the local SASE checkout at `9cb35859c9454b01d0d130e4cd74cb6d38f55251`, the linked Rust core at `f1ea08fbdeb7fe40271b369892c91750a0b5c947`, existing regression tests, and primary external sources. Repository links below are pinned to these revisions. I also opened the GitHub provider plugin through the required repository workflow; the relevant Git implementation proved to be in SASE itself. I did not inspect private historical agent outcomes or run paid model comparisons.

A small in-process probe using the workspace virtual environment and a fake provider confirmed the current inheritance behavior: passing `model_tier='small'`, `model_override='original-small-model'`, and explicit `reasoning_effort='low'` to `run_conflict_repair_turn` delivered those same arguments to the provider. The finalizer-owned marker was set during invocation and restored afterward, and usage was accumulated. This probe made no model call and performed no repair or repository mutation. The application test suite was not run for this research-only change.

**The current control flow already provides the right trigger.**

1. The Git commit path rebases onto the remote default branch and attempts a bounded deterministic resolver chain after a failed rebase. The chain recognizes bead data, artifact-link JSON, managed artifact-link Markdown, and plan-header conflicts. It declines sets containing unclaimed paths. These mechanisms already avoid model calls for some structured conflicts. Preserve them. [Git dispatch](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/vcs_provider/plugins/_git_commit_dispatch.py#L184), [semantic resolver](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/sdd/_semantic_conflict_resolver.py#L58).
2. The commit workflow checkpoints a paused operation and reports `RunResult.CONFLICT`; its CLI conflict exit code is `2`. The finalizer branches on `EXIT_CODE_CONFLICT`, then invokes `resolve_commit_conflict`. This is a better trigger than searching stderr for the word “conflict,” or escalating every nonzero stitch result. The workflow also recognizes an existing in-progress merge/rebase, so the trigger includes checkpointed paused-operation recovery rather than exclusively newly introduced conflict markers. [Workflow](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/workflows/commit/workflow.py#L207), [exit-code definition](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/workflows/commit/workflow_types.py#L21), [dispatch branch](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/finalizers/commit_dispatch.py#L398).
3. `resolve_commit_conflict` checks whether the repair allowance has been spent and calls `run_conflict_repair_turn`. That function directly invokes the supplied LLM provider with `purpose='conflict_repair'`, the inherited model override, and inherited options. The instruction boundary delivers an instruction bundle and calls that provider; it does not select a different provider. [Repair and bounds](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/finalizers/commit_repair_conflict.py#L80), [invocation](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/finalizers/commit_repair_conflict.py#L540), [instruction boundary](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/llm_provider/_instruction_boundary.py#L537).
4. The repair prompt already requires semantic resolution, review of the staged integration, checks from the target repository, attention to automatically merged content, continuation of the paused operation, and `sase stitch create --resume`. It prohibits bypassing the paused operation with a fresh stitch. Subsequent declared work is handled by a bounded host continuation. Escalation does not require rewriting these rules. [Repair prompt](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/finalizers/commit_repair_conflict.py#L461).
5. The repair is an inline, host-owned provider invocation inside finalization, not an ordinary independently scheduled successor. Its marker prevents turn-ending handoffs that cannot complete in this context. Afterward, the host inspects commit markers/checkpoints and repository state; it does not simply trust the model's closing message. [Ownership guard](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/finalizers/owned_turn.py), [resume verification](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/finalizers/commit_repair_conflict.py#L132).

There is a distinct missing/stale-declaration recovery path. Leave its model policy unchanged. Similarly, a push failure, a timeout, invalid commit metadata, and a later conflict beyond the continuation allowance must not acquire extra repair turns as a side effect of this feature. The existing tests explicitly cover another originally obligated repository receiving its own repair, while rejecting a second repair for the same repository and repair of newly introduced continuation work. The bound is not simply “one extra turn for the entire run.” [Declaration recovery](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/finalizers/declaration_recovery.py#L30), [multiple original repositories](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/tests/test_finalizers_protocol_harness_multi_repo_dispatch.py#L221), [continuation limits](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/tests/test_finalizers_protocol_harness_multi_repo_repair_edge.py#L104).

**Why I support the default.** A task can be cheap to implement yet difficult to integrate: a small edit may overlap a broader refactor or an unrelated contributor's change. The original task's model choice is therefore a weak proxy for repair difficulty. There is also only one permitted repair turn per repository in this path. Spending that opportunity on a weak inherited model before escalating would require changing the retry contract. Selecting the high-capability alias immediately is simpler and avoids another failure-and-recovery cycle.

The useful population is already filtered: conflicts resolved mechanically never need this model choice. That makes the policy more defensible than routing every Git conflict event or every commit to the most expensive model. It also avoids creating a fragile classifier based on file extension, hunk count, or an inexpensive model's self-assessed confidence. Markdown can encode critical instructions, JSON can contain identities that must be preserved, and a one-line code conflict can change behavior substantially.

**The main criticism is that capability does not replace evidence.** The current prompt correctly distinguishes clean conflict markers from a correct integration. Keep that distinction in the success criteria. A more capable model can still resolve ambiguity incorrectly, discard one side's intention, or produce changes outside the conflicted hunks that pass incomplete tests.

External evidence reinforces that caution without proving which current SASE alias is best. *Merge-Bench* evaluates 7,938 conflict hunks from 1,439 repositories. Its multi-language results report 52.6% normalized-code agreement for the strongest model in that experiment; a specialized 14B model also performs competitively on Java. The benchmark compares outputs with developers' committed resolutions, rather than proving program equivalence. It evaluates older models and snippet-based prompting, so its percentages should not be projected onto today's tool-using SASE agents. My inference is that model size alone is an inadequate acceptance rule; local repair correctness needs its own evaluation. [Merge-Bench, results and limitations](https://arxiv.org/html/2605.25890v1#S7).

There are two additional costs. A provider switch requires appropriate instruction delivery and can change latency, accounting, and available tooling. Also, the extra repair time extends the interval before publication, potentially exposing the run to more upstream movement. Whether these outweigh the quality gain is unknown without local measurements. The existing defaults make this especially relevant: `@xlarge` is currently an ordered chain beginning with Claude, followed by Codex and Grok, all annotated `@xhigh`; `@large` is a pool. A Codex-origin task can therefore repair under Claude. These are repository configuration facts, not claims about vendor model superiority. [Shipped aliases](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/llm_provider/models.yml#L259).

**Requirement adjustments I recommend making explicit.**

| Original implication | Recommended contract | Reason |
| --- | --- | --- |
| Always escalate on a conflict | Default every permitted finalizer conflict-repair model invocation to `@xlarge`, after existing deterministic handling | Avoid extra model calls and preserve the actual repair boundary |
| `@xlarge` means a strictly stronger model | It means the configured alias is selected afresh, including provider and effort | Alias overrides and cross-provider comparisons prevent a universal ranking |
| All inherited settings continue to apply | Inherit workspace, goal, declaration authority, and applicable instructions; replace task model and task effort for this repair | Otherwise the original low effort can defeat the intended policy |
| Always is immutable | Permit an explicit finalizer configuration override, including an explicit inherit mode for rollback | Allow cost/provider constraints and controlled comparison without changing global aliases |
| Escalation can fix a repeated failure | Preserve existing one-shot and continuation bounds | Model selection must not create unbounded retry or duplicate commits |
| Stronger model implies safe completion | Retain verification and host postcondition checks; allow an unresolved outcome | A clean merge or a confident answer is insufficient |

The override is a deliberate relaxation of “always,” not an accidental fallback. Under default configuration the rule is unconditional for every eligible repair invocation. The original task's `%model` or `%effort` should not implicitly opt out; opting out must name the finalizer policy. Existing explicit restrictions on allowed providers still apply.

**Place the policy in the finalizer's sealed configuration.** I recommend a provider-specific key under the existing instance `config`, with a default of `@xlarge` when omitted:

```yaml
finalizers:
  instances:
    commit:
      use: builtin@commit
      config:
        conflict_repair_model: "@xlarge"
```

Proposed semantics: a nonempty string accepts the supported model-expression grammar; an explicit `null` means inherit the original concrete provider/model/options; an omitted key means `@xlarge`. Reject empty strings, wrong types, unresolved aliases, and unsupported forms with actionable diagnostics. The distinction between missing and null must survive parsing and serialization. These are proposed semantics, not an existing option.

This location is preferable to changing `llm_provider.default_model` or inventing a sixth built-in role alias. It scopes the change to `builtin@commit`, supports custom instance names, and uses a configuration body already included in the instance digest. Current finalizer execution authenticates a sealed configuration snapshot and diagnoses live drift. Loading a new mutable setting inside the repair function would bypass that useful property. [Configured instances and digest](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/finalizers/config.py#L51), [sealed-plan authentication](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/finalizers/plan.py#L152).

Seal the requested expression and its provenance with the finalizer plan. Resolve the concrete route when a repair is actually needed, using current availability and the standard alias override rules, then record that choice once. This makes the distinction explicit: the policy is fixed for the run; runtime availability determines which eligible alias member executes. Do not repeatedly resolve the alias for display, logging, and execution. If aliases themselves can change during a run, record the effective alias chain at selection time so the choice is auditable.

**Implementation should have a small domain policy and a careful invocation adapter.** Shared routing behavior belongs in `sase_core`. Add a deterministic policy function and typed request/response in the existing `model_route` or finalizer domain: given the recovery kind and validated configuration, return inherit or the requested expression and source. Keep provider discovery, availability capture, environment management, instruction delivery, and subprocess invocation in Python. The Rust model-routing module already separates frontend-neutral selection from provider I/O; its finalizer module explicitly leaves recovery execution to the host. Add the binding and round-trip tests, then advance SASE's core revision pin. [Rust routing precedent](https://github.com/sase-org/sase-core/blob/f1ea08fbdeb7fe40271b369892c91750a0b5c947/crates/sase_core/src/model_route.rs), [Rust finalizer boundary](https://github.com/sase-org/sase-core/blob/f1ea08fbdeb7fe40271b369892c91750a0b5c947/crates/sase_core/src/finalizer/mod.rs#L1).

Thread the validated policy from `execute_commit_finalizer(instance, ...)` through dispatch into `run_conflict_repair_turn`. That last function is the natural execution point: it already owns the prompt, operation record, instruction purpose, and ownership guard. Avoid scattering the policy through every VCS backend or changing ordinary continuation model selection. [Commit executor](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/finalizers/commit_execution.py#L81).

The invocation adapter should follow this sequence:

1. Check the existing repair allowance and checkpoint ownership before admitting another model invocation. Select the requested expression from the sealed policy.
2. Capture a fresh provider-routing snapshot. Resolve the expression exactly once to the existing `LaunchSelection` shape, including provider, concrete model, effort, and alias provenance. Start with fresh repair directives so task-level effort cannot override alias effort. Reuse the existing resolver rather than copy its alias grammar or availability logic. Be careful: supplying the original `provider_name` prevents the normal model/provider-resolution branch in `resolve_launch_selection` from selecting another provider. [Launch selection](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/llm_provider/launch_selection.py#L264), [effort precedence](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/llm_provider/effort_resolution.py#L57).
3. Construct the selected provider and fresh invocation options. Preserve the supported execution-provider override used by test infrastructure. Scope and restore provider-specific synchronous hard/soft ceilings, instruction-delivery state, and any other per-provider execution context. Today the outer `invoke_agent` sets these ceilings from the original provider around the entire finalization call; simply swapping the provider in the inner call would leave stale ceilings. [Outer invocation setup](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/llm_provider/_invoke.py#L344), [execution-provider override](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/llm_provider/registry.py#L441).
4. Invoke through `invoke_with_instructions(..., purpose='conflict_repair')` inside the existing `finalizer_owned_turn()` guard. Preserve the run's artifacts, workspace/repository identity, goal binding, and finalizer authority. Do not recursively call the full `invoke_agent` lifecycle: it prepares finalizer plans and calls `run_finalizers` itself. Do not spawn a separate scheduled agent or add a monitor handoff to this inline path.
5. Persist the repair's actual selection and result, restore scoped state on success or exception, and return to existing resume/postcondition logic. Preserve per-provider usage evidence before aggregating totals with the originating turn.

Two tempting shortcuts are specifically wrong: `ModelTier` only permits `large` and `small`, so `model_tier='xlarge'` does not express the alias; and the plugin manager wraps one selected plugin, so `old_provider.invoke(model_override='@xlarge')` cannot by itself promise correct cross-provider dispatch. [Invocation types](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/llm_provider/types.py#L6), [plugin dispatch](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/llm_provider/_plugin_manager.py#L25).

Use standard alias availability behavior, including configured ordered alternatives and provider-disable rules. If the selected repair route cannot execute, report a typed failure and leave the paused operation recoverable. Do not silently substitute the original smaller model. Also distinguish pre-invocation availability fallback from an exception after an agent has already modified files: replaying the whole repair against another provider is another repair attempt, not harmless routing.

If the original turn already used `@xlarge`, still resolve the repair policy normally. It may pick the same concrete target, and that is acceptable. Do not force a provider switch to manufacture “escalation,” and do not add a speculative ranking table to retain a supposedly stronger manually selected model. An operator who wants continuity can explicitly choose inherit mode.

**Preserve recovery context and make the choice visible.** The repair prompt currently carries the target repository and procedure, but the prior `invoke_result.content` is appended to the eventual output rather than included as repair input. Neither same-provider execution nor an alias change should be assumed to preserve the original conversation. Ensure the repair can obtain the paused checkpoint, base/current/incoming revisions, relevant original intent, and target repository instructions through host-authorized references. Prefer a bounded evidence brief over replaying an entire transcript. Treat this as a context check accompanying the routing change, not a new summarization subsystem.

For Git specifically, identity should come from the paused operation and revisions, not casual interpretation of “ours” and “theirs”: rebase reverses the intuitive branch roles. The official documentation also recommends reviewing reused resolutions before staging when using `--no-rerere-autoupdate`. These are reasons to preserve semantic review even if a stronger model or cached resolution is used. [Git rebase documentation](https://git-scm.com/docs/git-rebase).

Record requested expression, policy source, alias trail, selected provider/model/effort, execution provider if overridden, previous selection, repository identity, invocation status, elapsed time, and available usage. Distinguish same-target selection from an actual provider/model change. Record failures as well as successes, and avoid relabeling the whole original run as if it had used the repair model throughout. `OperationRecorder.finish(extra=...)` is an existing place for supplementary evidence; persist selection before the call as well so failed invocations remain explainable. [Operation records](https://github.com/sase-org/sase/blob/9cb35859c9454b01d0d130e4cd74cb6d38f55251/src/sase/finalizers/operation_records.py#L99).

**Tests should prove routing and preserve the completion contract.** Add mocked invocation tests that assert the selected provider receives the concrete model and freshly resolved effort, including an original explicit low effort. Cover original small/large/xlarge selections; same-provider and cross-provider results; customized aliases; disabled/unavailable members; explicit inherit; custom finalizer instance names; configuration drift; and resolution/consumption exactly once. Verify execution-provider overrides and restoration of environment and instruction state after exceptions. Keep declaration recovery on its current policy.

Extend the existing real-Git protocol harness for a conflicted primary repository, a linked repository, and a sidecar; multiple originally obligated repositories; conflict on resume; repair that introduces a remaining obligation; and a second conflict that must stop. Preserve existing fixtures where the model already consumed the checkpoint so the host must not resume twice, and where successful resume leaves declared residue needing one follow-up commit. Include checks that network/push failures and output/timeout failures do not accidentally become new model-repair attempts. Existing test homes include `test_finalizers_commit_repair_prompt.py`, `test_finalizers_operation_records.py`, `test_commit_dispatch_conflict_repair_resume.py`, `test_commit_dispatch_conflict_repair_followup.py`, and the multi-repository protocol harness files cited above.

These deterministic tests prove correct policy execution, not that `@xlarge` merges better. Evaluate quality separately on a small, reviewed corpus of real SASE conflict checkpoints in isolated repositories, with no publication during evaluation. Compare inherit and `@xlarge` from identical starting states, stratifying source code, structured metadata, prose, and multiple-commit rebases. Track verified completion, preservation of both intended changes, later regressions/reverts, manual intervention, total elapsed time, and provider usage. Record actual concrete selections because mutable aliases can otherwise invalidate the comparison. Human review of ambiguous resolutions matters more than raw “Git is clean” rates.

The economic criterion is straightforward: the additional repair cost is worthwhile when the reduction in expected failure loss exceeds the added model and delay cost. Failure loss includes silent semantic regressions, manual recovery, and blocked publication. This report establishes neither the failure probabilities nor the costs; a rollout should measure them rather than claim savings in advance.

**Alternatives and their tradeoffs.**

| Alternative | Assessment |
| --- | --- |
| Keep inheriting the task model | Lowest implementation effort; continues coupling integration difficulty to the original task's model choice |
| Retry cheaply, then escalate | Adds latency and changes the one-shot contract; poor first choice here |
| Classify conflict difficulty and route selectively | Could reduce spend, but needs local labeled evidence and a measurable advantage over the simple rule |
| Prefer a stronger model only within the original provider | Reduces cross-provider work but does not implement the configured `@xlarge` policy; an explicit override can provide this preference |
| Deterministic resolvers and recorded resolutions | Valuable first line; retain current resolvers and consider targeted extensions when recurrent patterns justify them |
| Always ask a human | Appropriate when intent remains ambiguous or bounds are exhausted, but unnecessary as the default for every recoverable conflict |

Git's `rerere` can reuse previously recorded conflict resolutions, which may reduce repeated work. It requires an enabled and managed cache; introducing shared reuse across ephemeral workspaces needs its own correctness and lifecycle design. I would not couple that project to this routing change. [Git rerere documentation](https://git-scm.com/docs/git-rerere).

**Recommended solution.** Implement a sealed, per-commit-finalizer conflict-repair policy defaulting to `@xlarge`, with an explicit override and inherit escape hatch. Put deterministic policy selection in Rust and use a thin Python adapter to select and invoke the complete provider/model/effort tuple at the existing repair boundary. Preserve deterministic resolution, finalizer-owned execution, the current per-repository repair and continuation bounds, and semantic verification. Ship routing evidence and focused regression coverage with the change; use observed repair correctness, latency, and cost to decide whether selective escalation is later justified. This gives the one permitted model repair a strong default without confusing expensive execution with proven correctness.
