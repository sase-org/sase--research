# Plugin-Extensible Task Bead Types

**Research question:** How should SASE give task beads a required, plugin-extensible
type — with declared fields and a rendered description template — while keeping
generated agent instructions a function of the *project*, not of whichever plugins
happen to be installed on the current machine?

**Scope:** `sase` at `a383212a2`, `sase-core` at its linked checkout. Architecture
research; no runtime behavior changed. Consolidates two independent reports
([`__a`](task_bead_type_registry__a.md), [`__b`](task_bead_type_registry__b.md)) plus
verification of every load-bearing claim against the tree.

---

## Bottom line

1. **Add an orthogonal field, do not widen `IssueType`.** `IssueTypeWire` is a compiled
   Rust enum with **308** references in `sase-core` and **226** across **56** Python
   modules, and it carries nearly every structural invariant in the model. A compiled
   enum can never learn a slug a Python plugin invents. New field on `issue_type=task`
   only.

2. **Name it `task_type`.** Both `type` and `kind` are already taken — see §3.2. This
   is the one place the two source reports disagreed outright, and the evidence resolves
   it against both of their first choices' nearest rival.

3. **Copy `sase.artifact_providers` wholesale.** Declarative pluggy specs → central
   validation with provenance and structured diagnostics → Rust-computed stable digest.
   `FileHookProviderRecord` already carries `template` + `required_fields`, which is
   exactly the shape requested.

4. **Rust validates spec shape and slug shape; the *catalog* is enforced host-side in
   v1.** This is not a style preference — `provider_spec.rs` carries a written-down
   lesson that CI runs the *published floor* `sase-core-rs` against the checkout, so
   Rust-side enforcement of a new required field cannot be relied on until a core
   release lands and the floor is bumped. See §3.5.

5. **Determinism comes from a committed snapshot generated by `sase memory init`**, plus
   a new `plugins.required` project-config field. Both source reports invented this
   independently (`sase/task_kinds.yml` vs `task_types.lock.json`); they are the same
   artifact and it should ship in the same change as the registry.

6. **Agent instructions use the glossary's two-level split, verbatim.** AGENTS.md gets a
   generated `**TASK TYPES:**` paragraph of slugs + one-liners; detail is fetched with a
   CLI command. The glossary shipped this exact mechanism one commit ago
   (`a383212a2`), including an audited-read log.

7. **`bug` / `feature` / `memory` / `flake` / `ci` builtin (in Python); `github` in
   `sase-github`; `flag` stays `IssueType.FLAG` in core.** Do not create
   `sase-flag-tasks` for v1.

## 1. What exists today (verified)

### 1.1 Beads already have a type; tasks do not have a subtype

`IssueType = {plan, phase, task, flag}` (`src/sase/bead/model.py:20`), mirrored by
`IssueTypeWire` (`crates/sase_core/src/bead/wire.rs`). It is required, immutable after
create (`issue_updated` cannot change it), and it is the carrier of the invariants:

| Invariant | Enforced at |
| --- | --- |
| `phase` needs `parent_id`; `task`/`flag` must not have one | `schema.rs:44-48`, `model.py` |
| only `plan` carries `tier`, `is_ready_to_work`, Patch metadata | `schema.rs:50-52,57-60` |
| only `task` may be `ready` or `snoozed` | `schema.rs:53-55` |
| `flag` ⇔ `FlagRecord` present | `schema.rs:56` |
| `size` only on `phase`/`task` | `schema.rs:35-38` |
| unique `external_ref` index **excludes** flags | `schema.rs:78-81` |

There is **no** `metadata`, `extra`, `labels`, `kind`, or `category` column. `IssueWire`
does not `deny_unknown_fields`, so unknown JSON keys are silently dropped — relevant to
forward-compat (§3.5).

> **Correction to a claim in `__a`.** `__a` §1.3 reports a "split-brain" where the Rust
> wire allows `size` on flags but the SQLite CHECK does not. The CHECK
> (`schema.rs:35-38`) is real; whether the wire disagrees was not verified here. Either
> way the lesson stands: do not introduce a second field whose Rust and SQL constraints
> can drift.

### 1.2 `flag` is the existing proof-of-concept, hard-coded once

A required typed payload (`FlagRecord{key, remove_by_date, remove_by_release}`), a
dedicated creator (`sase flag new`), a dedicated gate with due-date rather than
corroboration semantics (`FlagTriage`, `flag_due.py`), dedicated presentation
(`⚑`, `#FF875F` — `bead_type_presentation.py:58-59`), and a CLI grammar that already
takes arguments. Generalizing that one shape *is* this feature.

### 1.3 The `-T` grammar already parses parameterized types

`parse_type_arg` (`src/sase/bead/cli_crud_create.py:31-91`) accepts exactly:

```
task
plan(<path>[,<parent_id>])
phase(<parent_id>)
flag(<key>,<YYYY-MM-DD>,<release>)
```

Bare `task` is the only unparenthesized form. Extending it to `task(<task_type>)` needs
no new flag, no `-T`/`--task-type` collision, and — importantly — keeps `flag` foldable
later without a grammar change.

### 1.4 `--size` is the precedent for "required going forward"

Rust enforces it at create only:

```rust
// crates/sase_core/src/bead/mutation.rs:201
if request.issue_type == IssueTypeWire::Task && request.size.is_none() {
    return Err(BeadError::validation(
        "new task issue creation requires an explicit size",
    ));
}
```

with a matching Python CLI error (`cli_crud_create.py:116-121`) and the documented
outcome in `sase/memory/sase_beads.md`: *"Every new task requires an intentional size…
Legacy sizeless tasks remain readable and launch through the small-task fallback."*
Copy this three-part shape exactly.

### 1.5 The store is event-sourced; `beads.db` is a rebuildable mirror

Canonical state is `beads/events/**`; `issues.jsonl` is a projection and `beads.db` is a
compatibility cache whose absence is only a doctor `WARNING`
(`crates/sase_core/src/bead/read.rs:251`). Reads reduce the event stream.

**This materially lowers the migration cost both reports worried about.** The SQLite
CHECK is not the load-bearing constraint — the wire and the reducer are. A new nullable
column on a rebuildable mirror is cheap. (`needs_issue_type_migration` /
`issue_type_migration_sql` at `schema.rs:85+` show the expensive table-rebuild path
exists, but a new column does not require it.)

### 1.6 The plugin substrate is mature and one subsystem is the right template

Eight entry-point groups (`src/sase/plugins/inventory.py:17-25`): `sase_artifact_refs`,
`sase_config`, `sase_file_hooks`, `sase_llm`, `sase_plugin_manifest`, `sase_vcs`,
`sase_workspace`, `sase_xprompts`. Four pluggy hookspecs exist. Only one is built for
*declarative* contributions rather than provider classes, and it is the newest:

- hook returns plain `Mapping[str, Any]` (`artifact_providers/_hookspec.py`);
- discovery collects builtin specs first, then entry points, each tagged with
  `ArtifactProviderProvenance{group, name, package, version, builtin}`, with per-plugin
  load-failure isolation into an `entry_point_load_failed` **error** diagnostic
  (`_discovery.py:47-105`);
- validation is centralized, dedupes by both id and kind with distinct codes
  (`duplicate_ref_provider`, `duplicate_ref_kind` — `_validation.py:68-88`);
- each spec gets a Rust-computed stable sha256 digest over the normalized spec
  (`artifact_ref/provider_spec.rs:178-188`);
- Rust already reserves slugs: `RESERVED_KINDS = ["stitch","patch","bead","agent","file"]`
  (`provider_spec.rs:27`);
- Rust already declares a **field type vocabulary**: `PROPERTY_TYPES = ["string","enum",
  "boolean","integer","number","date","datetime","string_list"]` (`provider_spec.rs:28-37`);
- `FileHookProviderRecord{provider_id, template, required_fields, provenance}`
  (`artifact_providers/_models.py`) is literally `template` + `required_fields`.

`sase-core` has **no plugin loader**; it validates plugin-produced JSON and owns the
closed enums. That division is the one to keep.

### 1.7 Generated agent instructions are committed and drift-gated

`sase validate` runs `("init","memory","--check")` first (`validate_handler.py:32`), and
`just check` runs `sase validate`. Generated `AGENTS.md` + provider shims are committed.
`src/sase/main/init_memory/staleness.py` exists *solely* to warn that "a foreign sase
build can silently answer a memory-drift check with different generator templates."

**Conclusion:** a task-type list read from the live plugin environment would red-build
whoever has the "wrong" plugin set, for a change they did not make. The user's
determinism instinct is not a nice-to-have; it is what makes the feature safe.

### 1.8 The glossary is the exact precedent, and it is one commit old

HEAD is `a383212a2 feat(glossary): add audited read and log dashboard`. The glossary:

- is declared in **project config** (`memory.glossary`), so it is deterministic;
- is validated and compiled **in Rust** (`crates/sase_core/src/glossary.rs`:
  `validate_glossary_entries`, `build_glossary_catalog`), with Python owning file
  discovery and source-preserving YAML parsing (`sase/core/glossary_facade.py`);
- renders into AGENTS.md Tier 2 as **names + aliases only**, with a pointer:

```python
# src/sase/amd/_memory.py:287-298
'**GLOSSARY TERMS:** Run `sase glossary read <term> -r "<why>"` before '
"relying on any of these SASE terms; it prints that term's definition "
"plus every term the definition depends on. Terms (aliases follow in "
f"parentheses): {entries}"
```

- and ships an **audited read** with a mandatory `-r/--reason` plus a log dashboard
  (`src/sase/glossary/{cli_read,cli_log,read_log}.py`, `sase glossary log`).

Everything §5 recommends for agent instructions is a mechanical extension of code that
landed in the last commit.

### 1.9 The instruction text already implies the taxonomy

`memory-sase.template.md:45-49` — the three "File Discovered Work As Task Beads" bullets
map one-to-one onto the proposed types (flaky-or-failing → `flake`/`ci`; stale memory →
`memory`; bug-or-improvement → `bug`/`feature`). The rewrite is a table, not a new
concept.

### 1.10 Triage policy is global today, and its predicates are pure

`bead.task_triage` in the project schema has exactly three knobs, all global:
`min_plus_ones` (default 1), `stale_after_days` (7), `stale_cleanup_min_beads` (10).
`src/sase/bead/task_triage_policy.py` is two **pure functions** — `task_gate_suppressed`
and `stale_task_bead` — whose docstrings state that callers own the clock and the
configured threshold. Per-type overrides are therefore a config-shape change plus a
threshold lookup, not a rewrite. This matters for §7.

## 2. External analogy (useful, not binding)

GitHub converged on the same three layers, which is weak but real evidence the split is
natural:

| GitHub (2024–2026) | SASE equivalent |
| --- | --- |
| Issue types (org-level: bug / task / feature) | `task_type` |
| Issue fields (text / number / date / single-select) | spec `fields` |
| Issue forms (YAML template filling the body) | spec `body_template`, rendered **below** description |

Linear and Jira mix workflow into custom issue types. SASE should not: every task type
keeps the existing task lifecycle. **A type that needs a different lifecycle is an issue
type, not a task type** — which is precisely why `flag` stays where it is (§8).

## 3. The decisions that matter

### 3.1 Where the type lives

| Option | Verdict |
| --- | --- |
| Widen `IssueType` to `bug`, `feature`, … | **Reject.** 308 Rust sites, a compiled enum plugins can never extend, and the §1.1 invariant table dissolves (is a `bug` allowed a `parent_id`? does it get `ready`?). |
| Free-form string `issue_type` | **Reject.** Same invariant loss plus every SQL CHECK. |
| **New orthogonal `task_type`, valid only when `issue_type == task`** | **Recommend.** `IssueType` keeps meaning "lifecycle family"; `task_type` means "flavor of discovered work". Purely additive. |

Both source reports reached this independently. It is the one unanimous structural call.

### 3.2 What to call it — resolved

`__a` argued for `kind`, on the grounds that `type` collides with `-T/--type`,
`sase bead list --type task`, ACE/search `type:`, `BeadTypeValue`, mobile `bead_type`,
and the `sase_beads.md` heading "Types, Tiers, And Launching". **Every one of those
collisions is real.**

But `kind` is *also* already taken, twice, and neither report noticed:

- **Gate envelopes.** `FLAG_TRIAGE_KIND`, `TASK_TRIAGE_KIND`, `BEAD_SNOOZE_KIND`,
  `BEAD_STALE_CLEANUP_KIND` — `envelope.get("kind")` is the gate discriminator across
  `src/sase/bead/{_task_gate_spec,_flag_gate_spec,snooze_gate,gate_lookup,...}.py`.
  Task-type work touches the gate preview path directly, so this is a live collision,
  not a distant one.
- **Artifact refs.** `ref.kind` is the provider discriminator, with `RESERVED_KINDS`
  enforced in Rust (`provider_spec.rs:27`) — the very subsystem this design copies.
- **Feature-flag registry.** `FeatureFlagDefinition.kind` ∈ `beta|wip|sunset|ops`.

**Recommendation: `task_type`** (`__b`'s choice). It collides with nothing, reads
unambiguously next to `issue_type`, and survives the moment when `flag` is folded in.
User-facing prose still says "task type"; agents type `-T "task(bug)"`.

### 3.3 How a type declares its fields

One declarative spec, identical whether it comes from a builtin, a plugin hook, or
project config:

```yaml
schema_version: 1
task_type: flake
label: Flaky test
summary: A test that passes and fails without a code change.
when_to_use: Use when a test failed and a rerun on the same tree passed.
glyph: "≈"
accent_color: "#5FD7AF"
fields:
  - name: node_id
    label: Test node ID
    type: string            # from the existing Rust PROPERTY_TYPES vocabulary
    required: true
    role: [data, template]
    help: The pytest node ID, e.g. tests/foo.py::test_bar
  - name: first_seen
    type: date
    required: true
    role: [data]
  - name: evidence
    type: string
    required: true
    role: [template]
body_template: |
  ## Flake report

  - **Test:** `{{ node_id }}`
  - **First seen:** {{ first_seen }}

  {{ evidence }}
triage:
  min_plus_ones: 1          # optional per-type override; see §7
create:
  default_size: small
```

Three refinements over what either report proposed:

1. **Reuse the existing Rust field-type vocabulary.** `__a` proposed
   `string|text|date|enum|ref|uint`; `__b` proposed `text|date`. Rust already validates
   `string|enum|boolean|integer|number|date|datetime|string_list` for artifact-ref
   properties (`provider_spec.rs:28-37`). Inventing a third list guarantees drift. Ship
   the scalar subset in v1 (`string`, `enum`, `date`, `integer`) and defer `string_list`
   until the storage question below is settled.
2. **Keep `__a`'s `role: [data, template]`.** `data` fields are filterable and appear in
   compact rows; `template` fields exist to fill the body block; most are both. `__b`'s
   spec had no way to say "this field is prose for the body, not a query key."
3. **Jinja2 with `StrictUndefined` is already the house engine**
   (`src/sase/mdtemplates.py`), so `body_template` adds no dependency and gets
   missing-variable-is-an-error for free.

`flag`'s current hard-coded `FlagRecord` is expressible as a three-field spec with no
`body_template` — a useful sanity check that the shape is general enough.

### 3.4 How field values are stored

| Option | Assessment |
| --- | --- |
| Render at create, append to `description`, store nothing | Rejected by both reports and correctly: unqueryable, the template can never be corrected retroactively, and `sase bead update -d` silently destroys it. |
| **Store a map; render the template at display time** | **Recommend.** Queryable, re-renderable, editable per field. |
| Typed per-type Rust structs like `FlagRecord` | Impossible for plugin types. |

Value type: `__a` said `BTreeMap<String, JsonValue>`, `__b` said
`BTreeMap<String, String>`. **Recommend `BTreeMap<String, String>` for v1**, with the
spec's declared `type` driving *validation and rendering* rather than storage. It keeps
the digest and the event diff unambiguous, matches how artifact-ref properties already
declare a `type` while their values arrive as markdown frontmatter text, and it is the
reason to defer `string_list` until there is a caller for it.

Non-negotiable: **`description` stays the human/agent free-text field.** The rendered
template appends *below* it and is never merged in.

Degradation when the plugin is absent: `sase bead show` prints the raw key/value pairs
under a `Task type: github (unknown to this machine)` header. Never a read failure.

### 3.5 How much does Rust validate? — resolved

This was the second real disagreement. `__a` wanted Rust to load the project catalog
snapshot and reject creates of unknown types. `__b` wanted Rust to validate slug *shape*
only, with catalog membership enforced host-side.

**The tree settles it.** `crates/sase_core/src/artifact_ref/provider_spec.rs:18-25`
carries this comment, written after the team hit exactly this problem:

> Adding `icon` as a required field is a breaking wire change, and the textbook move
> would be to bump this from 1 to 2. **Do not: CI installs the published floor
> `sase-core-rs` and runs it against this checkout**, which would reject a
> `schema_version: 2` spec before core carrying the bump is ever released. A floor core
> ignores an unknown `icon` field under serde's default handling and keeps validating at
> version 1, so enforcement simply does not apply until the core carrying it is
> installed.

So Rust-side enforcement of anything new is a two-release dance: land in core → release →
bump the `sase-core-rs` floor (cf. `88a840063 build(deps): require sase-core-rs 0.27.18`)
→ enforcement becomes real. Python-side enforcement lands in one release.

**Recommendation — `__b`'s split for v1, `__a`'s endpoint for v2:**

- **Rust v1:** `task_type: Option<String>`, `task_type_fields: BTreeMap<String,String>`
  on `IssueWire`; validate slug *shape* (non-empty, snake_case, bounded); validate
  cross-field consistency (`task_type` empty unless `issue_type == task`); validate and
  digest the *spec* wire type. Never a membership list, never a closed SQL CHECK.
- **Python v1:** owns discovery, the effective catalog, required-fields enforcement, and
  the create-time membership check.
- **v2, once the floor carries it:** move membership + field validation into
  `create_issue` against the snapshot, so a web app or editor gets the same guarantees
  without Python plugin discovery. This is `__a`'s argument and it is right — it is just
  a second step, not the first one.

**Forward-compat rule (both reports, correctly):** `task_type` must be a `String` on the
wire, never an enum. Bead stores are git-synced across machines; a bead authored with
`sase-github` installed *will* be read without it, and `IssueTypeWire` has no
`#[serde(other)]` fallback, so a new enum would be a hard deserialization failure.

### 3.6 Builtins in Python, not compiled into Rust

`__a` proposed compiling `bug`/`feature`/`memory`/`flake`/`ci` into `sase-core`; `__b`
proposed a `BuiltinTaskTypes` hookimpl in Python. **Python**, for the same
published-floor reason: builtins in Rust means every builtin tweak waits on a core
release, and `BuiltinArtifactProviders` (`artifact_providers/_builtin.py`) already
establishes that builtins register through the same hookspec from a host path inside
`sase`. Rust never needs to know the list.

## 4. Where the catalog comes from

```
builtin specs (sase, via BuiltinTaskTypes) ─┐
plugin hook specs (sase_task_types EPs)    ─┼─→ validate + dedupe + provenance ─→ TaskTypeRegistry
project config (bead.task_types)           ─┘          (+ diagnostics)
```

| Source | Mechanism | For |
| --- | --- | --- |
| Builtin | `BuiltinTaskTypes` implementing the hookspec | `bug`, `feature`, `memory`, `flake`, `ci` |
| Plugin | new `sase_task_types` group added to `ENTRY_POINT_GROUPS` (`plugins/inventory.py:17`) | `github` from `sase-github` |
| Project config | `bead.task_types:` in `sase/sase.yml` | project-specific types needing no code |

```toml
[project.entry-points."sase_task_types"]
github = "sase_github.task_types:GitHubTaskTypes"
```

```python
class TaskTypeHookSpec:
    @hookspec
    def task_type_specs(self) -> Iterable[Mapping[str, Any]] | Mapping[str, Any] | None:
        """Return declarative task-type specs."""
```

**Include project config as a third source** (`__b`'s recommendation; `__a` omitted it).
The glossary proves projects want pure-data vocabulary without publishing a Python
package, and it costs one `provenance.group` label and zero new validator code.

**Conflict policy** — copy `_validation.py` exactly: first candidate wins, later
duplicates dropped with a `duplicate_task_type` diagnostic naming the winner's
`provenance.label`. **Builtin slugs are reserved**; shadowing `bug` is an error
diagnostic, not a silent override. Also reserve `plan`, `phase`, `task`, `flag`, `type`.
Ordering must be deterministic: builtins, then entry points sorted by name (as
`discover_plugin_resources` already does), then project config in file order.

**Why pluggy and not the `sase_config` module pattern:** `sase_config` plugins export a
module whose attributes callers read; a bad one is a debug-log line. Task types feed a
*generated, committed* file, so a silently dropped type is a silently wrong AGENTS.md.
The pluggy path produces `error`-severity diagnostics that `sase doctor` already
surfaces.

## 5. Determinism: `plugins.required` + a committed snapshot

### 5.1 The failure being prevented

Agent A (has `sase-github`) runs `sase memory init`; AGENTS.md gains `github`; A commits.
Agent B (no `sase-github`) runs `just check` → `sase validate` → `init memory --check` →
drift → red build for a change B did not make. B "fixes" it by regenerating, and A goes
red.

### 5.2 `plugins.required` in project config

New top-level `plugins` key. Note `src/sase/config/sase.schema.json` is
`additionalProperties: false` at every level, and there is **no** `plugins` key today —
so this is a genuinely new schema section and must be registered.

```yaml
plugins:
  required:
    - name: sase-github          # distribution name, not the ProjectSpec key
      version: ">=0.4,<1.0"      # optional
    - name: sase-research-artifacts
```

This is **not** `repos.linked`: linked repos are source checkouts, required plugins are
runtime packages in the sase environment. A project can have a linked `sase-github`
checkout and still fail the check.

Enforcement graded by blast radius (merged from both reports):

| Surface | Behavior |
| --- | --- |
| `sase memory init` / `sase validate` | **Hard error.** Refusing to write a knowingly-incomplete AGENTS.md is the whole point. |
| `sase bead create -T "task(<plugin-slug>)"` | **Hard error** naming the plugin and the install command. |
| `sase doctor` | New `plugins.required` check, `ERROR`, beside the existing `plugins.resources` / `plugins.github` checks (`doctor/checks_plugins.py:32,38`). |
| Project enable / workspace open / ACE startup | **Warning + offer to install.** |
| `sase bead show` / `list` of an unknown type | **Never fails.** Degraded render. |

Version specs check against the installed distribution version, which
`plugins/inventory.py` already extracts.

### 5.3 The install-offer caveat neither report caught

`sase plugin install -h` states it plainly:

> This only works when sase was installed via `uv tool install sase` (the canonical
> install path). When run from a pip/pipx install or **a dev checkout's virtualenv**, it
> fails fast with an actionable message instead of touching your environment.
> … A successful install that changes packages **restarts axe**.

SASE runs agents from ephemeral `sase_<N>` workspaces, each with its own venv. **So an
agent cannot self-heal a missing required plugin** — `sase plugin install` will refuse,
and even if it did not, restarting axe from inside an agent turn is not something to do
silently.

Therefore: **fail closed in agent/non-interactive contexts** with the exact install
command aimed at the human's `uv tool` environment. Reserve the interactive
install-offer for ACE and the human CLI, behind a gate (`/sase_gate` is the house
mechanism). Do not auto-install from an agent.

### 5.4 The snapshot — both reports' idea, one artifact

`__a` proposed `sase/task_kinds.yml` written by `sase init`/`sase memory init`;
`__b` proposed `sase/task_types.lock.json` written by `sase memory init`. These are the
same artifact with different names and one different argument each, and both are right:

- **`__b`'s argument (content, not presence):** `plugins.required` guarantees the plugin
  is *installed*. It does not pin the *content* of its specs — bump `sase-github` 0.4.1 →
  0.5.0 with a reworded `summary` and AGENTS.md drifts again, on one machine first. The
  snapshot carries each spec's Rust-computed `digest`, so `sase memory init --check`
  reports *"`github` spec digest changed: sase-github 0.4.1 → 0.5.0; run
  `sase memory init`"* instead of an opaque AGENTS.md diff.
- **`__a`'s argument (a second frontend):** without a committed snapshot, a web app or
  editor cannot create typed tasks at all, because the catalog only exists inside Python
  plugin discovery. The snapshot is the rust-core-boundary-correct choice.

**Recommendation:** one committed file, `sase/task_types.json`, written by
`sase memory init`, containing `{slug, label, summary, fields, body_template, source,
package, version, digest}` per type. AGENTS.md renders **from the snapshot**, making it a
pure function of committed files — two machines produce byte-identical output.
`--check` diffs snapshot against live registry.

**Cost, stated honestly:** one more generated file to keep in sync and one more thing
`sase memory init` can fail on. Given that `--check` is wired into `just check` for every
agent, and given that `staleness.py` exists precisely because environment-dependent
`--check` answers are a known pain, it is worth it.

## 6. Agent instructions

**Never generate AGENTS.md or the global skill from "all installed plugins."**
`sase skill init` *does* depend on installed LLM plugins (deploy targets) — that is the
anti-pattern to avoid here.

| Surface | Contents | Source |
| --- | --- | --- |
| `/sase_new_task` (chezmoi-global, one per **machine**) | Workflow only: evidence, duplicate search, +1, epic note, then "choose a type from this project's catalog" and run `sase bead task-type show <slug>` | Skill template — **never** a project's type list |
| `AGENTS.md` Tier 1 (per **project**) | Generated `**TASK TYPES:**` paragraph: slugs + one-line summaries | The snapshot |
| `sase bead task-type list|show` | Runtime catalog and per-type field detail | Snapshot + builtins |

The AGENTS.md paragraph is the glossary block with the nouns changed
(`src/sase/amd/_memory.py:287-298`):

```
**TASK TYPES:** Every new task bead requires a type. Run `sase bead task-type show
<slug>` for a type's required fields before creating one. Types: bug; ci; feature;
flake; github; memory.
```

This replaces the three static bullets in `memory-sase.template.md:45-49`. The list is
short enough to inline and long enough that inlining every field spec would bloat every
agent's context — the tradeoff the glossary already resolved this way. Consider adopting
the glossary's audited-read shape (`-r/--reason` + `sase bead task-type log`) if you want
the same visibility into whether agents actually read type specs before filing.

`/sase_new_task` also changes in two places: step 4/5 searches gain `--task-type <slug>`
(search same type first, then all tasks — semantic duplicates legitimately cross types,
e.g. a `flake` that is really a `ci` failure), and step 7 gains the type choice. Epic
phase workers still never create beads; that rule is orthogonal.

**Naming note:** `sase bead` has no `type` or `kind` subcommand today, so the namespace
is free. Per `sase/memory/cli_rules.md`, a `sase bead task-type` group with an exact
`list` child auto-defaults to `list` when invoked bare, and every public long option
needs a short alias.

## 7. Making it required, and the policy payoff

### 7.1 Required-ness

Follow `--size` exactly:

1. **Wire/read:** optional forever. Existing beads without a type stay valid.
2. **Create:** required. Bare `-T task` errors *and prints the available types*.
3. **Display:** a typeless legacy task renders as `untyped` — a presentation label, not
   a catalog member, never offered at creation.

**No heuristic backfill.** A wrong type on hundreds of historical beads is worse than an
honest `untyped`, and the store is event-sourced, so a bulk rewrite is a real event-stream
mutation. A doctor-assisted opt-in reclassification can come later.

**`task_type` should be mutable via `sase bead update`** (`__a`'s call; `__b` was silent).
Misfiles happen, `issue_updated` is a sparse field list that already carries `size`, and
unlike `issue_type` no invariant depends on it. Add it to `BeadIssueUpdateFieldsWire`.

### 7.2 The per-type policy split — resolved

`__b` argued per-type triage thresholds should ship in v1 because they are the reason to
make the field required. `__a` argued v1 types must not register custom gates. **Both are
right about different things; ship the split:**

- **In v1: per-type `min_plus_ones` and `stale_after_days` overrides.** These are pure
  config on two pure functions (`task_triage_policy.py`), the config block
  (`bead.task_triage`) already exists with the right three knobs, and the change is a
  threshold lookup keyed by type. A `ci` failure should raise a gate at zero
  corroboration; a `feature` suggestion should probably need two.
- **Not in v1: custom gates.** A type that needs a different *gate kind* (as `flag` does,
  with its due-date `FlagTriage`) is asking for a different lifecycle — which is an issue
  type, not a task type. Defer.
- **`create.skip_triage` is not needed.** `__a` proposed it for the GitHub mirror. The
  mirror already creates beads at `status=open`, never `ready`, and `task_gate_suppressed`
  only fires on `ready` — so today's "never flood TaskTriage" behavior is preserved for
  free by `create.default_status: open`. One fewer knob.

Later, once the field is proven: per-type default size, per-type presentation
(`bead_type_presentation.py` currently hard-codes four glyph/accent entries), and
per-type declaration of `external_mirror` participation replacing the implicit
`external_ref` convention.

## 8. `flag` and `github`

### 8.1 `flag` — do not migrate, do not extract (unanimous)

Both reports independently recommend against the prompt's `sase-flag-tasks` plan, and the
evidence is strong:

- `flag` is an `IssueType`, not a task subtype. Migrating rewrites `issue_type` in an
  event-sourced store, and every §1.1 invariant shifts: flag beads would become eligible
  for `ready`, `snoozed`, and `+1`, none of which is meaningful.
- Its gate is due-date-driven (`FlagTriage`, whose Remove branch *launches a removal
  agent*), not corroboration-driven.
- `FlagRecord` has real Rust validators (snake_case key, ISO date, semver-ish release); a
  generic string map loses that unless spec fields grow validators.
- Flag beads are **deliberately excluded** from GitHub mirroring (`docs/beads.md`) and
  from the unique `external_ref` index (`schema.rs:78-81`). Prior feature-flag research in
  this same month directory is unanimous that the scarce resource is *deletion*, enforced
  by a local bead + gate + lint. A GitHub issues repo cannot replace that loop.
- Only the *bead* side could move. The registry (`feature_flags/registry.py` plus
  `tools/check_feature_flags` in `just validate` and `doctor/checks_flags.py`) is
  code-owned in the sase tree, and `sase flag new` refuses to run outside a SASE-managed
  checkout. A plugin owning the bead while core owns the registry is a genuinely awkward
  seam.

`__a` frames the honest long-term path as a separate capability — plugin-registered
*first-class issue types* with custom payload and custom gate — and that is right. It is a
multi-epic change and must not gate v1. `__b`'s three-phase staging is the same shape:
v1 registry → per-type gate policy and field validators → only then reconsider `flag`.
Either way, `flag` is untouched by this work.

### 8.2 `github` — spec in the plugin, mirror in core (unanimous)

Mirrored issues are *already* `task` beads: `external_issue_mirror` and
`sase bead sync-external` create `task`, `size=small`, `status=open`, with
`external_ref=bug:<project-key>#<n>` and a matching `bug:<display-name>#<n>` ref. The
labor split is already clean — provider-neutral `IssueWire` in sase, `gh issue *` in
`sase-github`, reconciliation in `external_mirror`, `external_ref` uniqueness in
`sase-core`.

So: **do not add an `IssueType.GITHUB`.** Give those beads `task_type=github` whose
*spec* (label, when-to-use, presentation, `default_status: open`) lives in `sase-github`,
and leave the mirror engine in core. If a second host appears, it registers its own type
and the mirror looks up "the type that claims this provider"; until then, hardcoding
`task_type=github` when the VCS plugin is `github` is fine. A project that mirrors GitHub
issues should list `sase-github` in `plugins.required`.

## 9. The catalog

| Type | Location | v1 fields | Notes |
| --- | --- | --- | --- |
| `bug` | builtin | `location` (string, req, data+template), `repro` (req, template), `impact` (opt, template) | Agent-found defect in unrelated work; not an external tracker bug. |
| `feature` | builtin | `proposal` (req, template), `why_out_of_scope` (req, template) | The `why_out_of_scope` field is what keeps this from becoming a wish list. |
| `memory` | builtin | `path` (string, req, data+template), `proposed_change` (req, template) | `path` is worth validating against `sase/memory/*.md` — a builtin-only capability. Close ritual stays "user permission + `sase memory init`". |
| `flake` | builtin | `node_id` (req, data+template), `repro_cmd` (opt, data+template), `evidence` (req, template) | `evidence` covers fail rate, soak, serial-vs-parallel — the distinctions `parallel_suite_flake_triage.md` shows actually matter. |
| `ci` | builtin | `node_id` (req, data+template), `sha` (opt, data), `why_not_flake` (req, template) | `triage.min_plus_ones: 0` — a confirmed red build should not wait for a second reporter. |
| `github` | `sase-github` | none beyond `external_ref` | `create.default_status: open`. Spec + presentation travel with the plugin that implements the tracker. |
| `flag` | **stays `IssueType.FLAG`** | — | §8.1. |

`ci` had no stated LOCATION in the prompt; **builtin** is right — it is the complement of
`flake`, used by the same agents on the same lint/test path, with no plugin dependency.
Putting it in a plugin would make the sase project's own instructions require that plugin.

Keep field counts small. Types grow fields additively; removing a required field is a
spec major version. `untyped` is a legacy presentation label, never a choice.

## 10. Recommended solution

### Rollout order (forced by the published-floor constraint, §3.5)

**Step 1 — `sase-core`, released and floor-bumped before Step 2 depends on it:**

- `task_type: Option<String>` and `task_type_fields: BTreeMap<String,String>` on
  `IssueWire`, `BeadCreateRequestWire`, and `BeadIssueUpdateFieldsWire`.
- Validate: slug shape; both empty unless `issue_type == task`. **No membership list, no
  closed SQL CHECK** — plugin types are an open set.
- New `task_type` TEXT column + `CHECK(task_type IS NULL OR issue_type='task')` on the
  rebuildable `beads.db` mirror.
- `TaskTypeSpecWire` + `task_type_spec_validate` / `task_type_spec_digest`, mirroring
  `artifact_ref/provider_spec.rs` and reusing its `PROPERTY_TYPES` vocabulary.
- Pure `render_task_type_body(spec, fields) -> markdown`.

**Step 2 — `sase`:**

- `sase_task_types` pluggy hookspec + entry-point group added to `ENTRY_POINT_GROUPS`;
  `BuiltinTaskTypes` with `bug`/`feature`/`memory`/`flake`/`ci`; `bead.task_types` as a
  third source. Central validator producing `TaskTypeRecord{...provenance, digest}` plus
  `TaskTypeDiagnostic`s; builtin and reserved slugs protected; first-wins dedupe.
- Create-time enforcement in Python: `-T "task(<slug>)"` (extending `parse_type_arg`),
  repeatable `-f/--field k=v` for values awkward inside parentheses, bare `-T task` errors
  with the type list.
- `plugins.required` in `sase/sase.yml` + `sase.schema.json`; graded enforcement per §5.2;
  new `plugins.required` doctor check; **fail closed in agent contexts** (§5.3).
- `sase memory init` writes `sase/task_types.json`; AGENTS.md renders the
  `**TASK TYPES:**` paragraph from it; `--check` diffs snapshot vs live registry with a
  digest-level message.
- `sase bead task-type list|show`; `--task-type` filter on `list`/`search`.
- `/sase_new_task` + `memory-sase.template.md` + `sase_beads.md` updated (with explicit
  user permission per the memory-edit rule).
- Per-type `min_plus_ones` / `stale_after_days` overrides threaded through
  `task_triage_policy.py`.
- Surfaces: ACE create modal type picker, `bead show` / TUI detail / bead pages render the
  template below the description, TaskTriage preview shows type + fields, mirror sets
  `task_type=github`, JSON/mobile gain `task_type`/`task_type_fields` while `bead_type`
  keeps meaning `issue_type`.

**Step 3 — `sase-github`:** register the `github` spec. No store changes, no new issue
type.

**Step 4 — this project's `sase/sase.yml`:**

```yaml
plugins:
  required:
    - name: sase-github
    - name: sase-research-artifacts
```

### v1 non-goals

Extracting `flag`; plugin-defined issue types or custom gates; historical backfill;
per-type duplicate policy; `.github/ISSUE_TEMPLATE` files; `string_list` field type;
Rust-side catalog membership enforcement (that is v2, once the floor carries it).

### Agent-facing examples

```bash
sase bead create -T 'task(bug)' -t "parse_type_arg rejects unknown subtypes as phase" \
  -d "…" -z large -f location=src/sase/bead/cli_crud_create.py -f repro="…"

sase bead create -T 'task(flake)' -t "test_bar failed 3/20 under xdist" -z medium \
  -f node_id=tests/test_foo.py::test_bar -f evidence="passes serially, fails at -n8"

sase bead create -T 'task(memory)' -t "sase_beads.md still documents -T task with no type" \
  -z small -f path=sase/memory/sase_beads.md -f proposed_change="…"
```

`/sase_new_task` still runs first; the type is chosen in step 7, not instead of the
duplicate and epic sweep.

### Why this over the alternatives

Widening `IssueType` cannot work — compiled enum, 308 sites, invariant loss. A pure-config
approach with no plugin hook cannot express `github` (which needs code for mirror
participation) and forfeits the diagnostics that make a dropped type visible in a
generated, committed file. Rendering AGENTS.md from the live plugin environment is
simpler than a snapshot but reintroduces exactly the drift `staleness.py` already exists
to warn about. Migrating `flag` first maximizes risk on the least-understood part of the
design before the cheap types have proven the registry.

The recommended path is additive at every layer, reuses one already-shipped and
already-validated pattern (`artifact_providers`) plus one shipped last commit (the
glossary block) rather than inventing new ones, and makes the single genuinely new risk —
machine-dependent agent instructions — impossible by construction rather than by
convention.

## 11. Risks

| Risk | Mitigation |
| --- | --- |
| Agents keep typing `-T task` | Hard error printing the catalog; updated skill + AGENTS.md paragraph |
| Snapshot drifts from installed plugins | `sase memory init --check` / doctor compare digests |
| Two plugins claim `bug` | First-wins + doctor ERROR; builtin and reserved slugs protected |
| Agent hits a missing required plugin and cannot install it | Expected — fail closed with a human-directed command (§5.3); never auto-install from an agent |
| Rust enforcement assumed live before the floor bump | Keep v1 enforcement in Python; treat Rust checks as belt-and-braces until the floor moves |
| `task_type_fields` becomes a junk drawer | Small builtin schemas, few required fields, template is display-only |
| `flag` gets "type-ified" during review | §8.1; put it in the plan's explicit non-goals |
| SQL `CHECK (task_type IN (...))` temptation | Open TEXT column; validate in code, never in an SQL IN-list |
| A `type`/`kind` name sneaks back in | §3.2; both are already taken, twice over for `kind` |
