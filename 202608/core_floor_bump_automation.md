# Automating the `sase-core-rs` Dependency-Window Bump

**Research question:** SASE agents are repeatedly tasked — by task beads, by dedicated
epic phases, and by mid-task discovery — with raising the `sase-core-rs` version window
in `sase`'s `pyproject.toml`. What is the cheapest correct way to take that work off
agents entirely?

**Scope:** `sase` at master `9bce277c9`, the linked `sase-core` checkout at master
`b8b6570` (v0.21.3 plus six unreleased commits), the PyPI release metadata for
`sase-core-rs`, the GitHub release-PR history of `sase-org/sase-core`, and the 67
commits in `sase` history that have touched the dependency line. All measurements were
taken on 2026-08-09 and every reproduction in the appendix was run, not inferred.

## Bottom line

1. **The decision this work exists to make is already fully computable, and nobody
   computes it.** `tools/check_sase_core_rs_bindings --list` emits the exact set of 265
   core bindings `sase` requires, and `tools/validate_sase_core_rs` probes the wire
   schemas it requires. Both are stdlib-only and import nothing from `sase`, so
   "does published `sase-core-rs==V` satisfy this tree?" is a bare venv plus two
   commands. Bisecting that oracle over published versions yields the correct floor in
   seconds. Today an agent reaches the same answer by hand, by reading core git history.
2. **The dominant cost is not the edit — it is the wait, and the wait is human.** The
   machine half of a `sase-core` release is a near-constant **9.5 minutes** from
   release-PR merge to wheel-on-PyPI (10 samples, 7m45s–13m20s). The human half —
   release-PR creation to merge — has a median of **~43 minutes**, a mean of ~2h20m, and
   a worst observed case of **9h37m**. That variance is why plans keep spawning a
   separate "wait, then bump" phase bead instead of doing it inline.
3. **The edit itself is three files and one of them shouldn't exist.** Every pure bump
   touches `pyproject.toml:46`, `uv.lock` (regenerated), and one hardcoded literal in
   `tests/test_sase_core_rs_telemetry_smoke_tool.py:35`. That literal is redundant with
   the synthetic-fixture test directly beneath it and is pure friction.
4. **This is high-volume and accelerating.** 67 commits have moved the line since
   2026-04-29; **35** of them were bump-focused commits that existed for no other
   purpose. Over the last five days the rate is ~1.8/day. 187 of 3547 plan files mention
   `sase-core-rs` and 47 carry explicit floor/window-bump language.
5. **Recommendation: a "core floor ratchet"** — a deterministic `tools/required_core_floor`
   oracle, a `just` gate that reports the answer during normal verification, a
   deterministic `just bump-core-floor` apply path, auto-merge on `sase-core` release-plz
   PRs to collapse the wait, and an axe chop that fires the whole thing unattended. Full
   detail in [§7](#7-recommendation). The agent-facing cost goes from "an agent
   investigates, waits, edits, and verifies" to zero for the common case.

## 1. What the work actually is

A pure floor bump is a three-file mechanical change. Every bump-only commit in the
history has an identical shape:

```
 pyproject.toml                                  |  2 +-
 tests/test_sase_core_rs_telemetry_smoke_tool.py |  2 +-
 uv.lock                                         | 14 +++++++-------
 3 files changed, 9 insertions(+), 9 deletions(-)
```

— `491579083` (`build(deps): raise sase-core-rs floor to 0.20.0`), and identically
`7bdeee08e`, `6488d4a49`, `8cc3913fc`, `10843b522`.

The three sites are the only places the version is written:

| Site | Change | Derivable? |
| --- | --- | --- |
| `pyproject.toml:46` | `"sase-core-rs>=X,<Y"` | yes — this *is* the decision |
| `uv.lock` | regenerated by `uv lock` | yes — mechanical |
| `tests/test_sase_core_rs_telemetry_smoke_tool.py:35` | `assert tool.declared_minimum_version(...) == "0.21.3"` | yes — and it should not be a literal at all |

That third site deserves a note. It is a golden literal asserting that
`declared_minimum_version` reads the real `pyproject.toml` correctly. The very next test
in the same file (`test_declared_minimum_requires_inclusive_floor`) already proves the
parser's behaviour against a `tmp_path` fixture. The literal therefore adds no coverage
the file lacks; it only guarantees that every floor bump must edit a test file.

### Volume

35   of those whose subject is *about* the bump (build(deps)/fix(deps)/"raise the floor"/

47   plan files contain explicit floor / dependency-window bump language

The rate is not incidental: `sase-core` published 20 releases in the seven days

## 2. Where the tokens actually go

The work decomposes into four costs, and they are not equally expensive.

### A. Diagnosis — "which floor do I need, and why?"

This is the most token-expensive part and the most completely automatable. The canonical
artefact is task bead `sase-hz`, whose description is roughly 40 lines of forensics
produced by a landing agent:

> ROOT CAUSE: `src/sase/core/glossary_facade.py` (added by `544e98a19`, phase `sase-hq.1`)
> calls `require_rust_binding('glossary_validate')`, `('glossary_catalog')`, and
> `('compile_glossary_catalog')`. Those bindings come from sase-core commits `f6a29d3`
> and `943af9b`, which landed on sase-core master AFTER the v0.21.0 release tag —
> `git ls-tree -r v0.21.0 | grep glossary` is empty.

That whole investigation resolves to one computed number. Reproduced mechanically in
about ten seconds:

```
$ git tag --contains f6a29d3 --sort=v:refname | head -1
v0.21.1
$ /tmp/pc-0.21.0/bin/python -c "import sase_core_rs as m; print([x for x in
    ('glossary_validate','glossary_catalog','compile_glossary_catalog') if hasattr(m,x)])"
[]
$ /tmp/pc-0.21.1/bin/python -c "... same ..."
['glossary_validate', 'glossary_catalog', 'compile_glossary_catalog']
```

The bead's conclusion — "raise to `>=0.21.1`" — is the output of a five-line script.

### B. The wait — the required release is not on PyPI yet

This is the structural cost and the reason plans create a *separate phase* for the bump.
Two hard gates enforce it:

- `just check` runs `just validate`, which runs
  `tools/validate_sase_core_rs_version --pyproject pyproject.toml --published-minimum`.
  That performs a live PyPI lookup and **fails if the declared minimum is not
  published**. An agent cannot legitimately bump ahead of the release.
- `uv lock` cannot resolve a floor that does not exist on the index.

So the agent's options today are: block and burn a phase bead on polling, or file a task
bead so a *later* agent redoes the whole context load. Both are what the user is
observing. §5 quantifies the wait.

### C. The mechanical edit and re-verification

Three files, then `just check-full` (the change touches `pyproject.toml`, a broadening
path). The edit is trivial; the verification is expensive in wall clock but needs no
judgement. Note that in a fresh ephemeral workspace this also pays a `just install` that
rebuilds the Rust core from source.

### D. Planning overhead

47 plan files carry explicit bump language, and `sase-i8.8` shows the shape: a
first-class phase bead, with its own `DEPENDS ON` / `BLOCKS` edges, whose entire
description is:

> floor: after the core release publishes, move the sase-core-rs version window in
> pyproject.toml to the release that carries the schema-3 contract and confirm the
> exhaustive gate passes against the published wheel.

Every such phase is a bead, a launch, a workspace claim, and a context load — for a
three-file deterministic edit.

## 3. What already exists (do not rebuild it)

The repo is much further along than a naive reading suggests. Any solution should
compose these rather than replace them.

| Asset | What it already does | Gap |
| --- | --- | --- |
| `tools/check_sase_core_rs_bindings` | Statically collects the 265 `require_rust_binding` names from `src/sase` and asserts an installed wheel exposes them. Has a `--list` mode that needs no wheel at all. Stdlib-only. | Only ever run in CI, against one version. Never asked "which version *would* satisfy this?" |
| `tools/validate_sase_core_rs` | Probes wire-schema versions (`artifact_ref_wire_schema_version: 4`, `vcs_log_wire_schema_version: 3`, `sase_content_layout schema_version: 5`) and behaviour contracts. Stdlib-only. | Same. |
| `tools/validate_sase_core_rs_version` | Compares the checkout's Cargo version to the specifier with directional exit codes (3 = behind, 4 = ahead); `--published-minimum` verifies the floor exists on PyPI. | Compares to the *checkout*, not to what the source tree needs. |
| `tools/validate_test_environment` | Caches and dispatches the above, with a bit-mask verdict the `Justfile` acts on. | — |
| `Justfile` `_core-overrides-arg` | Deliberately lifts the published window for dev installs so local core may run ahead. | This is *why* local dev cannot see the skew — intentional, keep it. |
| `.github/workflows/publish.yml` | Already has a bot that runs `uv lock` and commits the result to a release branch. | Direct precedent for a bot-authored lock refresh. |
| Axe (`sase axe chop`) | A first-class scheduler for exactly this shape of recurring, script-driven, proposal-emitting work — `ci_watch`, `refresh_docs[...]`, `toobig_split[sase]` are live examples. | No chop watches the core floor. |
| `plans:202608/stale_core_binding_guard.md` | Landed the *behind*-direction guard (exit codes 3/4, fatal `_setup`, installed-version check). | Explicitly scoped out "raising the `pyproject.toml` floor again". |

The critical, non-obvious enabler: **both probe tools are stdlib-only and import nothing
from `sase`.** Verified — `tools/validate_sase_core_rs` imports only `argparse`,
`importlib`, `json`, `sys`, `tempfile`, `pathlib`, `types`, `typing`. That means
"does published `sase-core-rs==V` satisfy this source tree?" is answerable in a throwaway
venv containing nothing but the candidate wheel. That is the whole oracle.

## 4. The gap: the required floor is computable, and nothing computes it

`pyproject.toml` records a floor that a human/agent *chose*. Nothing in the repo derives
the floor the source tree *needs*. Closing that gap converts the entire diagnosis cost
(§2A) into a script.

### Ground truth must be introspection, not source scanning

I prototyped a git-archaeology approach first — regex `#[pyo3(name = "...")]` out of
`crates/sase_core_py/src/lib.rs` at each tag — and it is **wrong**. It found 280
exported names where the built wheel exposes 309 (0.21.0) and 313 (0.21.1): it misses
`#[pyclass]` types, functions without an explicit `#[pyo3(name)]`, and anything added via
`m.add(...)`. Running that as a gate would produce confidently incorrect floors.

`dir(sase_core_rs)` on the actual wheel is the ground truth, and it is cheap: a
`sase-core-rs` wheel is ~5 MB and installs in a couple of seconds.

### The algorithm

```
required   = tools/check_sase_core_rs_bindings --list          # no wheel needed
candidates = published sase-core-rs versions within the declared upper bound (PyPI JSON API)
satisfies(V):
    uv venv $tmp; uv pip install "sase-core-rs==V"
    $tmp/bin/python tools/check_sase_core_rs_bindings   # binding names
    $tmp/bin/python tools/validate_sase_core_rs         # wire schemas + behaviour probes
floor = lowest V in candidates where satisfies(V)       # binary search; monotone in practice
```

Both probes are already written. Because the export set of a published version never
changes, the per-version verdict is cacheable forever — steady state is one wheel
download per new core release, and zero on a cache hit.

The result should be a small JSON verdict, not a bool:

```json
{
  "declared":  ">=0.21.3,<0.22.0",
  "required":  "0.22.0",
  "state":     "blocked_unpublished",
  "missing":   ["parse_merge_summary"],
  "provided_by": [{"binding": "parse_merge_summary", "commit": "459bbc6",
                   "subject": "feat(vcs-log): add parent ids and merge summaries",
                   "released_in": null}],
  "pending_release_pr": "sase-org/sase-core#101"
}
```

with distinct exit codes for `ok` / `stale_actionable` (the needed version *is* published
— bump now) / `blocked_unpublished` (waiting on a core release). The `provided_by`
attribution is the only part that needs core git history, and it is presentation, not
decision: `git log --reverse -S'<name>' -- crates/sase_core_py/src/lib.rs` then
`git tag --contains`. Both verified working in the appendix.

That single object is everything bead `sase-hz` spent an agent producing.

**Merged → PyPI: mean 9.5 min, range 7m45s–13m20s.** The machine half is effectively a
constant.

**PR open → merged: median ~43 min, mean ~2h20m, max 9h36m.** The two worst cases are
overnight. This is the entire variance, and it is a human clicking Merge on a PR that
contains nothing but a version number and a changelog.

`sase-org/sase-core` has `allow_auto_merge: false` and master is **unprotected** — so the
release PR is gated on attention, not on policy. This is the single highest-leverage
lever in the whole problem: enabling auto-merge on release-plz PRs collapses the
end-to-end core-change → PyPI path from a median ~52 min / worst ~9h45m to a predictable
~15 min, and largely dissolves the reason a plan would allocate a separate "wait, then
bump" phase.

## 6. Options considered and rejected

**Track "latest published" unconditionally (Renovate/Dependabot-style).** A bot bumps the
floor to whatever `sase-core-rs` published most recently. Simple, and it matches what
most historical bumps did anyway. Rejected as the *primary* mechanism: at 3–5 core
releases/day it generates 3–5 lock-churning PRs/day, each needing green CI, and it
gratuitously narrows the accepted window for published `sase` installs for releases
`sase` does not use. Worth keeping as a slow (daily) backstop *behind* the computed
ratchet, not instead of it. Off-the-shelf Renovate is additionally a poor fit here
because the interesting constraint is a `>=` floor tied to symbol availability, not a
lock pin.

**Publish a `sase-core-rs` dev release on every core master commit** (e.g.
`0.21.4.dev3+g1a2b3c`). Removes the wait entirely — `sase` could floor on the exact
commit. Rejected: it pollutes the public PyPI project that end users install from,
complicates resolution for published `sase`, and multiplies the wheel matrix cost
(4 platform builds + sdist per commit) by an order of magnitude.

**Runtime feature detection with graceful degradation.** Make `sase` tolerate a missing
binding instead of pinning a floor. Rejected: `tools/check_sase_core_rs_bindings`' own
docstring records why the strict gate exists — sase 0.11.0 shipped calling an unreleased
binding and every published install crashed on first render. Degradation trades a loud
build-time failure for a quiet runtime one.

**Merge `sase-core` into `sase` (monorepo).** The deepest fix: the entire problem class is
an artefact of cross-repo release coupling, and a single release train deletes it. Listed
for completeness — it is a large migration with real costs (Rust toolchain in every
`sase` CI lane, slower installs, loss of the independent core release cadence) and is
disproportionate to the pain being solved. Note it *would* also delete the
`published-core-minimum-smoke` lane and the whole dev-build-ahead override machinery.

**Just write a better prompt for the bump agent.** Cheapest to try, and it does reduce
per-bump tokens. Rejected as the answer: it leaves the work agent-shaped, so it still
costs a bead, a launch, a workspace claim, and a full context load per bump, ~1.8 times a
day. The task has no judgement in it; it should not have an agent in it.

**Relax the CI gate so master does not go red while a core release is pending.** Tempting,
since the red lane is what makes each bump *urgent*. Rejected: the red lane is the only
thing that catches this class before it reaches users, and with a fast ratchet the window
where it can be red shrinks to ~15 minutes. Weakening the gate to buy time you no longer
need is a bad trade.

## 7. Recommendation

A **core floor ratchet**, in five pieces. R1–R3 are self-contained and independently
valuable; R4 is the highest leverage per unit of effort; R5 is what removes agents from
the loop entirely.

### R1 — `tools/required_core_floor` (the oracle)

New stdlib-only tool implementing §4. Emits the JSON verdict; exits `0` (ok), `3`
(`stale_actionable`), `4` (`blocked_unpublished`), `1` (internal error), matching the
directional-exit-code convention `stale_core_binding_guard.md` already established.
Caches per-version verdicts under the managed SASE temp/state root so steady state is one
wheel download per core release.

Reuses `check_sase_core_rs_bindings --list` and `validate_sase_core_rs` unchanged — this
is roughly a bisect harness plus a PyPI version listing, not new validation logic.

### R2 — Surface it in `just check`

Add a `core floor` step alongside the existing `SASE validation` gate. `stale_actionable`
should fail with the exact remediation (`just bump-core-floor`); `blocked_unpublished`
should **warn, not fail**, and name the blocking core commit and pending release PR.

This closes the hole that produced `sase-hz`: today the only thing that notices a
required-but-unpublished binding is a CI lane, so an agent lands the feature, master goes
red, and a *second* agent is dispatched to investigate. With R2 the first agent is told,
before it commits, exactly which core release it needs and that it is not out yet.

### R3 — `just bump-core-floor [--to X]` (the deterministic apply)

Rewrites `pyproject.toml`'s specifier, runs `uv lock`, and re-runs the published-wheel
probes against the new floor. Defaults `--to` to the oracle's `required`.

**Also delete the golden literal.** Change
`tests/test_sase_core_rs_telemetry_smoke_tool.py:35` to assert against a value derived
from `pyproject.toml` rather than the hardcoded `"0.21.3"`. The synthetic-fixture test
below it already covers the parser. This drops the bump from three files to two, and
removes the one edit site with no mechanical justification.

### R4 — Auto-merge release-plz PRs in `sase-core`

Enable `allow_auto_merge` on the repo and have the release-plz workflow set auto-merge on
the release PR, gated on its CI. Per §5 this is where the hours live: it turns a
median-43-minute / worst-9h36m human gate into a green-CI condition, making
core-change → PyPI a predictable ~15 minutes end to end.

Low risk: release-plz only opens a release PR when releasable commits exist, the PR
contains only a version bump and changelog, `sase-core` CI already gates it, and the
publish job independently verifies the tag and the wheel metadata before uploading. The
project is 0.x with a fully automated wheel matrix; a release is cheap.

This is the one change that makes the *wait* stop being a thing a plan has to model.
Recommend doing it first — it is a settings change plus a few workflow lines, and it
delivers value even if R1–R3, R5 are never built.

### R5 — Axe chop `core_floor_ratchet`

A chop on a slow lumberjack (housekeeping, ~1h, or `checks` at 5m) that runs the R1
oracle against the `sase` project:

- `ok` → nothing.
- `stale_actionable` → propose one tightly-scoped agent whose entire job is
  `just bump-core-floor && just check-full && commit`. With R1–R3 that agent makes no
  decisions and needs almost no context; it is a candidate for a cheap model. Use
  `once_per` keyed on the target version so it proposes exactly once per core release.
- `blocked_unpublished` → record and stay quiet. This is the state that currently
  generates forensic task beads; it should generate nothing at all, because R4 means it
  resolves itself within minutes.

Axe is the right host: `ci_watch`, `refresh_docs[...]` and `toobig_split[sase]` are the
same shape (script decides, runner launches), and the chop framework already provides
cadence, dedupe, guards, and per-project fan-out.

### R6 — Planning guidance (requires explicit user approval)

Once R1–R5 land, plans should stop allocating a dedicated "raise the sase-core-rs
dependency window" phase — the ratchet owns it. That is a change to plan-authoring
guidance and possibly to `sase/memory/`, which under this repo's rules needs explicit
user permission in-conversation; it is listed here as a proposal, not an action.

### A useful adjacent gap

`%wait` supports agents, beads, time floors, and runner thresholds, but has no predicate
for external state — there is no `%wait(published=sase-core-rs>=0.22.0)`. Adding one would
let a plan express "this phase starts when the core release exists" as a machine wait
rather than a phase bead that polls. Worth considering independently; with R4 in place it
is much less urgent, so it is noted rather than recommended.

### Suggested order

1. **R4** — settings + a few workflow lines; removes the hours.
2. **R1 + R2** — the oracle and the gate; removes the diagnosis cost and stops master
   going red by surprise.
3. **R3** — the apply path; makes the remaining work a one-liner.
4. **R5** — the chop; removes the agent.
5. **R6** — guidance, once the machinery is proven.

R4 alone is likely the best effort-to-value trade in the whole list. R1+R2 alone would
have prevented bead `sase-hz` from ever being written.
