# Goals as durable outcomes and a verification inbox

**Recommendation:** Build Goals. Make a goal the durable *outcome* behind work, not a synonym for an agent, plan, bead, or notification. Bind every LLM work agent to exactly one primary goal **at launch**, reuse that binding through the workflow, and let the agent submit an evidence-backed completion *claim* through a required host finalizer. Keep the claim visible until a human accepts or rejects it. This moves attention from “an agent stopped” to “an outcome is ready to check.”

This synthesis incorporates all four independent reports: [cdx](goal_outcomes_and_verification__cdx.md), [grk](goal_outcomes_and_verification__grk.md), [mus](goal_outcomes_and_verification__mus.md), and [gem](goal_outcomes_and_verification__gem.md). I also checked the current launch, finalizer, prompt archive, artifact-link, notification, and TUI code in `sase` and the wire/domain boundary in `sase-core`. The reports agree on host-owned binding and goal-based attention. Their substantive disagreements are whether Goals should be beads, where durable state belongs, how strong closure evidence must be, and where the TUI inventory belongs.

## Why the idea is good—and what I would change

An agent completion is a process event. The user cares about an outcome: one research synthesis may require four researchers and a lead; one epic may take a planner, several phases, retries, and a land agent. Conversely, an ad-hoc answer can satisfy an intent without a plan or commit. One goal can span many agent runs and artifacts; each agent run has one primary goal. Other goals may be linked as context, but only the primary one receives that run's finalizer decision.

The proposed `SASE_PLAN` check and mandatory `/sase_new_goal` skill are the wrong enforcement point. `src/sase/agent/launch_spawn.py` deliberately removes inherited `SASE_PLAN`; approval and attach paths set it selectively. Skills can be skipped, and four parallel researchers could create four copies of one goal. The launcher already knows the prompt, plan, bead, lineage, and eventual agent ID. It should establish the goal before invoking the model. An optional goal skill is useful for inspecting or splitting a goal, but never for the invariant.

**Explicit adjustments to the request:**

1. **No planner exemption.** A planner has a purpose. Give it the incoming outcome goal at launch; `sase plan propose` attaches/refines that goal and hands it forward. If the user asked only for a plan, the plan artifact can satisfy a plan-delivery goal. Reuse the existing PlanApproval attention instead of issuing a duplicate Goal alert.
2. **“All agents” means all LLM agent shells, including hidden helpers.** Mechanical monitor, gate, and `%proc` shells inherit goal context where relevant but are not independent goal claimants. Hidden/system agents bind to a parent or internal goal and cannot close a user goal without explicit delegation. This preserves the invariant without cluttering the user's view.
3. **“Done” means human-settled for the performance target.** An agent's `close` is a *claim*, entering `needs_review`; it remains in the hot set. `verified`, `waived`, `canceled`, and `superseded` are cold terminal states. Thus the hot list is `O(n_unsettled)`—active work plus awaiting-review claims—and settled history has no foreground cost.
4. **Cross-machine means local-fast and explicitly fresh, not globally instantaneous.** A Git-backed remote cannot make an offline machine see a new goal immediately. Show a sync watermark and pending-publication state; require successful publication for a strict shared launch/close. Projects without an initialized, consented shared sidecar need an explicit local-only mode or must refuse the shared guarantee.
5. **Evidence is policy-sensitive.** A reply can evidence an answer goal; a plan needs its validated plan artifact; a code change needs the host-finalized change plus any verification receipt required by its acceptance criteria. A blanket “test command required for every goal” would make questions and documentation goals impossible. Plain assertion text is never sufficient on its own.

## What exists today and what is missing

Tale and epic plans already have a required `goal` string (`src/sase/sdd/plan_validate.py`, Rust-backed). The runner stores the exact launch-boundary prompt in `submitted_xprompt.md` before xprompt expansion; `raw_xprompt.md` is a different, alias-resolved form (`src/sase/axe/run_agent_runner_setup_prompt.py`). These are useful provenance, but the canonical agents-sidecar prompt archive currently publishes primarily for agent-backed commits and approved plans (`docs/agents_sidecar.md`). A question answered without either path needs a new publication path if its original prompt is to remain available on another machine.

The finalizer framework already has host-issued, digest-bound context, a turn nonce, required instances, ordered execution, and a `bead_action` precedent (`crates/sase_core/src/finalizer/wire.rs`, `src/sase/default_config.yml`). Today `defaults: [commit]` and `required: []`; a normal goal-bound run would need `builtin@goal` required regardless of repository dirtiness. Successful user-agent completion currently emits `JumpToAgent` tagged `done` (`src/sase/axe/run_agent_runner_finalize.py`). Merely adding Goal notifications would leave the old unread noise intact; the cutover must change that path.

The artifact relation registry is closed (`docs/artifact_links.md`), so goal links require a deliberate schema extension. The TUI currently has exactly `Agents | Artifacts | Services` (`src/sase/ace/tui/tab_order.py`) and an existing Artifacts pane contract plus relation rail. The shared goal model, transitions, evidence validation, and artifact-kind rules belong in `sase-core`; Python should orchestrate I/O and Textual presentation. A new binding used by Python requires the corresponding `sase-core-revision.txt` ratchet.

## Recommended model and lifecycle

Use an opaque stable `goal:<id>` artifact with title, outcome statement, optional acceptance criteria, creator and project, origin prompt locator/digest, plan and bead refs, visibility (`user` or `internal`), revision, and current status. The title can change; the ID cannot. The exact creator's **submitted unit prompt** is an immutable, content-addressed snapshot. Also record the upstream/root prompt or group digest for transformed fan-outs, and attach each later contributing agent's submitted prompt and global agent identity. Do not call expanded system instructions the “original prompt,” and do not inline potentially private prompt bodies in list rows.

```text
active ── completion claim + evidence ──> needs_review
   ▲                                      │  │
   └──────── reject + feedback ──────────┘  └── accept/waive ──> verified/waived
active ── explicit cancellation/supersession ──────────────────> canceled/superseded
```

All normal provider returns choose `keep_open` or `close` in the Goal finalizer. `keep_open` needs a short progress reason and does not notify. A crash or kill cannot choose: the host records failed/aborted work and keeps the goal active. `sase pipe`, questions, gates, and plan proposal are intentional handoffs; they transfer/keep the binding in their host-owned handoff transaction. Prepared monitor completion carries a predeclared choice: green may close, red keeps open and launches recovery. Retries and follow-ups inherit the same goal. A sibling or phase may not close while required contributors remain live; a designated coordinator/lander should make the outcome-level claim.

At launch, resolve in this order: associated plan's persisted `goal_id` (or deterministically create it from a legacy plan ref and its required `goal` text); explicit operator goal selection; parent/session/pipe/recovery inheritance; exact structured bead or epic identity when unique; otherwise create an ad-hoc goal from the submitted prompt. Show semantic matches as suggestions only. Never silently join two goals on fuzzy text similarity. Reject binding to a settled goal unless it is explicitly reopened or a linked follow-up goal is created. Persist the binding with agent metadata, expose `SASE_GOAL_ID` as a convenience, and inject the goal statement into agent instructions; the environment variable is not the source of truth.

## Closure evidence and finalizer contract

Add a non-removable `builtin@goal`, ordered **after** `builtin@commit`, triggered even on clean trees. The host issues a goal obligation containing the ID, revision, criteria, closure eligibility, and available evidence candidates. The submitted action is compact: `keep_open` with reason/next step, or `close` with a specific claim, criterion-to-evidence mapping, a short human verification hint, and disclosed limitations. The host checks revision and eligibility again at execution time; if commit or monitor results change the context, stale declarations are rejected and recovered.

| Goal outcome | Minimum durable evidence | Host checks |
| --- | --- | --- |
| Answer or review | Captured response/transcript artifact | Digest and association to the closing run; “read the answer” is a valid verification hint. |
| Research or document | Registered report/file ref | Ref resolves to the produced version; claim points to the relevant finding or section. |
| Plan delivery | Validated archived `plan:` ref | Proposal/approval handoff state; no duplicate PlanApproval alert. |
| Code or operational change | Host-finalized stitch/Patch or immutable output ref, plus required check/monitor receipts | Commit finalizer succeeded; refs and receipts exist; required acceptance criteria are met or an earlier human policy waived them. |

The agent may explain *why* evidence supports the claim, but cannot manufacture a successful command, artifact ref, or verification policy. A self-written “tests passed” sentence is not a receipt. For code work lacking a required verification result, keep the goal open or present the limitation for an explicit human waiver; do not have the agent waive its own criterion on the closing turn. Evidence is support for a human judgment, not a proof that the world is correct. `close` publishes a `completion_claimed` event containing accepted refs and their digests; the artifact-link projection is derived from that event, so a claim cannot be visible without its evidence links. Notification emission follows durable publication and is idempotent on the claim ID.

This addresses a timing gap in the reports: a stitch created by `builtin@commit` does not exist when the model submits its manifest. Let the agent select pre-existing refs and a host-provided “current commit result” token; the goal finalizer resolves that token to the actual stitch after commit. A reply-only run may likewise need the host to publish its response snapshot before an `agent:` page exists remotely.

## Durable storage and genuinely fast reads

Prefer the existing private **agents sidecar**, because it already holds agent identities and prompt objects, uses a hidden machine-owned clone, and has publication/retry machinery. Extending it is still real work: it currently publishes mostly on commits/approved plans, so goal create/attach/claim/settle must become independent host publication paths. Do not put the canonical goal in workspace-local `agent_meta.json`, the notification inbox, or the bead event log. Respect the sidecar's privacy and disabled settings; adding launch prompts to it is a publication decision, not a harmless cache change.

Store immutable, schema-versioned, per-goal events (`created`, `agent_attached`, `plan_attached`, `completion_claimed`, `verification_accepted`, `reopened`, etc.) with actor, basis revision, and idempotency key. Publish prompt objects, new events, and **per-goal hot snapshots** together in a Git transaction. Keep unsettled snapshots in `goals/live/<id>.json`; settlement removes that hot file and leaves archived history. A machine-local compact projection accelerates frequent CLI/TUI reads and can be rebuilt from the synced `live/` directory, including on a fresh machine, without replaying closed history. Build/repair from the full event history only off the foreground path. The first Git clone still transfers repository history; the `O(n)` promise is for the active-goal query and warm/fresh local projection, not for network bootstrap or repair.

The foreground `sase goal list` reads only the compact hot projection: one bounded record per unsettled goal, no historical filter, and no synchronous pull. The TUI paints that cached view, refreshes off the event loop, and shows last sync/pending changes. Avoid sorting the entire hot set on every read if strict linear complexity matters; store display order in the projection or use a linear stable partition for `needs_review` vs `active`. A SQLite local read model with a partial index is an alternative if update and query patterns outgrow a compact file; [SQLite's documented partial indexes](https://www.sqlite.org/partialindex.html) include only qualifying rows. A query-optimized projection and its staleness/rebuild costs are established [CQRS](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs) and [materialized-view](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view) tradeoffs.

A directory split alone does **not** guarantee zero Git conflicts or atomicity: two machines can edit the same goal, and writing an archive file then deleting an active file is not an atomic local transition. The publisher must lock locally, apply event plus projection as one repository commit, pull/recompute on non-fast-forward, validate `basis_revision`, and push with bounded retry. On conflicting concurrent claims or attachments, retain/reopen `active` with a conflict diagnostic rather than choose by timestamp. Report success only once the shared write is confirmed; queue/recover a failed publication without emitting a false “ready to verify” alert. Measure cold-start rebuild and sync lag separately from hot-list latency.

## Navigation and attention design

Place a **Goals pane inside Artifacts** for the full inventory, with an Agents-tab goal chip/header and a `by goal` grouping mode. This fits the existing three-tab chrome and artifact relation rail better than a fourth top-level tab. It also gives Goals a stable project-wide home outside whichever agent is selected. The pane's default has two clear lanes: **Needs review** first, then **In progress**. A compact row shows status, title, project, last activity, and contributor count. Detail shows the outcome, original-prompt preview with explicit open action, plan/bead, contributing agents, the claim, evidence refs, and a short “How to verify” checklist. The empty state explains that new work receives a goal at launch. Use one restrained accent and readable status text, never color alone.

Add `goal` as a first-class artifact kind and one projected `agent pursues goal` relation. Derive plan-definition and evidence links from durable binding/claim records rather than letting users hand-edit generated pages. Existing relation rail/trail and jump hints should open a selected goal's plan/report/stitch, or select a specific contributor on the Agents tab; the latter must work even if the agent row is currently grouped or collapsed. Keep the origin prompt accessible without flooding the default list. Add `sase goal list/show/verify/reopen` equivalents to every TUI action so the interface is not the sole control path.

One `needs_review` transition sends one `JumpToGoal` attention item with the claim and verification hint. `keep_open` and intermediate agent completion remain visible as execution history but no longer create default user-completion unread dots or chimes. Operational failures, questions, and approvals keep their own attention routes. Reading/dismissing a notice is not verification; explicit **Verify**, **Waive**, or **Reject and reopen** settles it. Rejection records feedback and offers (but does not silently force) a successor. Existing PlanApproval should suppress a duplicate plan-only goal alert. Remote attention must surface the same goal claim across machines, deduplicated by goal/claim identity.

## Why the alternatives lose

- **Bead-backed Goals (mus):** This reuses lifecycle and sync, but task beads encode scheduling, size, phase ancestry, and close semantics. Making every answered question a bead would inflate a tracker already dominated by closed records; the existing `sase bead list/stats` path is history-scaled. A special Python-only goal bead would also violate the shared Rust domain boundary. Link goals to beads instead.
- **Separate goals sidecar (gem's alternative):** A clean privacy/lifecycle boundary, but adds another repository to configure, clone, sync, repair, and authorize. Reuse the agents sidecar initially; revisit separation only if its access policy or publication load proves incompatible.
- **Top-level Goals tab (cdx):** Gives strong prominence, but a fourth global tab adds navigation and persistence cost while the Artifacts shell already provides list, detail, links, and cross-tab jumps. Start with a built-in Artifacts pane plus an Agents context surface. A top-level tab can follow usage evidence.
- **Mandatory evidence triad (gem):** Command witness + artifact + rationale fits many code changes but excludes legitimate answers and plan-only goals. Require resolvable outcome evidence and a human check instruction; add test receipts when the goal's policy demands them.
- **Agents-only Goals deck (mus):** Keeps jumps local but makes a project-wide verification inbox dependent on the selected agent and risks overwhelming the Agents tab. Use an Artifacts inventory and a small Agents context block.

## Implementation sequence and acceptance tests

1. Define Goal wire model, transitions, prompt provenance, artifact identity, and publication protocol in `sase-core`; add Python binding and ratchet the pinned core revision. Build the independent publisher and hot projection first. Test two-machine same-goal races, interrupted publication, cold-machine bootstrap, stale projection, privacy-disabled projects, and local-only policy.
2. Integrate launch binding across direct runs, plan approval, bead work, swarms, child launches, retries, pipes, monitors, gates, and hidden helpers. Backfill existing active plans deterministically; leave historical completed agents as legacy/unbound rather than invent their goals. Test that every *new* LLM agent starts with exactly one primary goal and a durable creator prompt.
3. Add required `builtin@goal` and prepared-monitor/handoff handling. Validate evidence by outcome type, current revision, live contributors, and actual host receipts. Test close-before-commit, failed monitor, deferred/failed commit, duplicate submit, and concurrent close/reopen.
4. Add goal notification and explicit verify/reopen actions; then retire ordinary success-completion attention. Keep errors and decisions visible. Ensure one published claim yields at most one notification across retries and machines.
5. Add the Artifacts Goals pane and Agents goal context, reuse relation navigation, and benchmark active-list/read responsiveness against increasing *settled* history. Verify `p95` hot-list latency and TUI frame budget on each supported machine rather than asserting “sub-millisecond” without measurement.

**Recommended solution:** A first-class, host-bound Goal artifact in `sase-core`, published with immutable prompt and lifecycle evidence through the existing agents sidecar, queried from a hot unsettled-goal projection, claimed complete by a required goal finalizer, and presented as an Artifacts-pane verification inbox with direct links back to agents and evidence. This retains the strongest ideas from all four reports while keeping scheduling, process completion, and human verification distinct.
