**Status**: Completed

## 1. Executive Summary

Maintaining SASE's built-in size model alias pools (such as `@xsmall`, `@small`, `@medium`, `@large`, `@xlarge`) alongside the models supported by completion in the ACE prompt input widget and external editors (via the `sase-xprompt-lsp` Rust language server) has become a notorious maintenance tax.

An empirical analysis of recent commits introducing or bumping models reveals the extent of this friction:
- **Grok 4.7 Support (`1cea18e00f`)**: **19 files** changed, 345 line diffs.
- **GPT-6 Sol Selection (`682089c845`)**: **28 files** changed, 260 line diffs.
- **Retune Size Aliases to Effort Ladder (`65c8169f9d`)**: **16 files** changed, 221 line diffs.

The user's objective—enabling maintainers to update both size alias pools and completion models by touching as few files as possible/desirable—is **strongly validated and overdue**. However, a naive consolidation (e.g., merging everything into an ad-hoc configuration file without architectural decoupling) introduces severe hazards:
1. **Conflation Hazard**: The *universe of completable models* across providers (e.g., legacy, mini, or specialized models) is significantly broader than the *curated, effort-laddered subset* assigned to size aliases.
2. **The "Test Tax" Trap**: Over 70% of the files touched in historical bumps were **brittle unit tests** asserting literal model name strings (e.g., `test_load_balanced_alias_defaults.py`, `test_model_picker_options.py`, `test_xprompt_model_completion_catalog.py`). If the test architecture is not decoupled into property/invariant checks, editing a single config file will still break 8 to 12 test files across the suite.
3. **Documentation and Instruction Drift**: Markdown tables in `docs/llms.md` and default config comments in `default_config.yml` require manual updates unless automated.

### Core Recommendation
We recommend implementing a **Unified Declarative Model & Alias Manifest (`src/sase/llm_provider/catalog.yml`)** accompanied by a **four-pillar decoupling strategy**:
1. **Unified Manifest**: Co-locate provider model declarations (known models, short display aliases, reasoning effort support, tier defaults) and size alias definitions (`@xsmall`..`@xlarge` pools and fallbacks) in a single, schema-validated YAML file.
2. **Default Hook Delegation**: Built-in `LLMProvider` plugins (`claude.py`, `codex.py`, `grok.py`, etc.) automatically delegate their `llm_known_model_names()` and `llm_model_short_aliases()` hooks to this central catalog, preserving third-party pluggy extensibility while eliminating boilerplate.
3. **Invariant & Fixture Testing**: Refactor test suites to validate *structural invariants* (Decision 15 effort ladder compliance, provider diversity, target resolvability) rather than hardcoded model strings. Tests verifying exact routing mechanics use frozen synthetic fixtures (`tests/_model_alias_defaults_fixture.py`).
4. **Zero-Touch Editor & LSP Parity**: Preserve the existing `MODEL_COMPLETION_CATALOG_SCHEMA_VERSION = 1` JSON wire contract generated by `model_completion_catalog_payload()`. This guarantees that neither the Rust `sase-xprompt-lsp` binary nor the ACE Textual UI widgets require code changes.

With this architecture, adding a new model and assigning it to size aliases drops from **16–28 files down to 1 file (`catalog.yml`)**, with zero broken tests and automatic documentation synchronization.

## 2. Current State Architecture and Root Causes of Pain

### 2.1 How the System Works Today

The current model discovery and alias resolution pipeline is split across two disjoint subsystems:

```
[ Provider Plugins (Python) ]                    [ Model Alias Defaults (YAML) ]
  src/sase/llm_provider/codex.py                    src/sase/llm_provider/model_alias_defaults.yml
    - llm_known_model_names()                         - xsmall, small, medium, large, xlarge
    - llm_model_short_aliases()                       - target: "claude/opus@high | codex/gpt-6-sol@xhigh..."
    - _TIER_TO_MODEL                                  - description: ...
               │                                                      │
               ▼                                                      ▼
  [ LLM Registry (_registry_catalog.py) ]          [ Model Alias Policy (model_alias_policy.py) ]
    - get_llm_metadata_payload()                     - parse_model_alias_selector()
               │                                     - Decision 15: size-alias-effort-ladder
               │                                                      │
               └──────────────────────┬───────────────────────────────┘
                                      ▼
                      [ Completion Catalog Builder ]
                     sase.xprompt.model_completion
                      - build_static_model_completion_catalog()
                      - ModelCompletionEntry (wire v1)
                                      │
                   ┌──────────────────┴──────────────────┐
                   ▼                                     ▼
        [ ACE Prompt Input Widget ]           [ External Editors (LSP) ]
          Textual directive_completion          xprompt_lsp._materialize_model_catalog()
          Rust filter_model_completion_entries    Writes: model_catalog.json
                                                  Consumed by: sase-xprompt-lsp (Rust)
```

1. **Model Discovery & Completion**:
   - Each provider plugin in `src/sase/llm_provider/` implements `LLMHookSpec` methods via `pluggy`:
     - `llm_known_model_names() -> list[str]` (e.g., `gpt-6-sol`, `gpt-5.6-terra`, `o3`).
     - `llm_model_short_aliases() -> dict[str, str]` (e.g., `{"gpt-6-sol": "gpt6sol"}`).
     - `llm_resolve_model_name(tier) -> str` (`large` vs. `small` mappings).
   - `sase.llm_provider.registry` aggregates these into `get_llm_metadata_payload()`.
   - `sase.xprompt.model_completion` transforms this metadata into a list of `ModelCompletionEntry` objects.
   - For ACE TUI: `directive_completion.py` calls `build_model_completion_catalog()` and filters candidates via `sase_core_rs.filter_model_completion_entries`.
   - For external editors: `sase.integrations.xprompt_lsp._materialize_model_catalog()` writes `sase_subdir("xprompt_lsp") / "model_catalog.json"` with schema version 1, which `sase-xprompt-lsp` reads on completion triggers.

2. **Size Alias Pools**:
   - `src/sase/llm_provider/model_alias_defaults.yml` claims to be the "single edit point" for `@xsmall`, `@small`, `@medium`, `@large`, and `@xlarge`.
   - Each alias specifies a `target` selector (e.g., `"claude/opus@high | codex/gpt-6-sol@xhigh | grok/grok-4.7@xhigh"`).
   - This file is governed by **Decision 15: Size Aliases Descend The Effort Ladder (`size-alias-effort-ladder`)**:
     - Scanned from `@xlarge` down to `@xsmall`, a model's first appearance runs at `xhigh`.
     - Each subsequent appearance must drop exactly one rung of `EFFORT_LEVELS_ORDERED` (`xhigh` → `high` → `medium` → `low` → `minimal`).
     - Aliases must maintain multi-provider redundancy (at least 2 providers per pool/fallback).

### 2.2 Why Maintenance Is Currently Painful

When a maintainer updates a model (e.g., promoting a new model version and incorporating it into `@large` or `@medium`), they face a sprawling web of manual updates:

| Category | Files Requiring Edits | Failure Mode / Maintenance Friction |
| :--- | :--- | :--- |
| **Provider Code** | `src/sase/llm_provider/<provider>.py` | Modifying Python lists and dicts (`llm_known_model_names`, `llm_model_short_aliases`, `_TIER_TO_MODEL`). Risk of syntax errors, missing shorthands, or tier inconsistencies. |
| **Alias Config** | `src/sase/llm_provider/model_alias_defaults.yml` | Rewriting selector strings; manual effort-ladder calculation across 5 tiers. |
| **Brittle Unit Tests** | `tests/llm_provider/test_load_balanced_alias_defaults.py`<br>`tests/test_xprompt_model_completion_catalog.py`<br>`tests/test_model_picker_options.py`<br>`tests/llm_provider/test_ordered_fallback_aliases.py`<br>`tests/test_llm_provider_<provider>_basic.py` | Tests assert exact string literals: e.g. `assert "gpt-6-sol" in model_entries`, or `assert alias == "codex/gpt-5.6-terra"`. A model bump breaks 5–10 tests that were asserting old names rather than behavior. |
| **Documentation** | `docs/llms.md`<br>`docs/ace.md`<br>`docs/configuration.md`<br>`docs/getting_started.md` | Hand-maintained Markdown tables: "Automatic Provider Resolution" table (lines 1655–1664) and "Model Short Aliases" table (lines 1692–1700). Frequently drift out of sync. |
| **Example Config** | `src/sase/default_config.yml` | Commented-out example alias blocks (lines 1548–1554) drift from shipped defaults unless manually mirrored. |
| **UI Modals** | `src/sase/ace/tui/modals/...` | Placeholders like `placeholder="e.g. codex/gpt-6-sol@medium"` get out of date. |
| **Decision Memory** | `sase/memory/decisions/size-alias-effort-ladder.md` | Narrative examples referencing specific models (e.g., Grok 4.7 vs. 4.6) require editing to stay accurate. |

This fragmentation means a maintainer cannot simply "change a model"; they must perform an audit of 20+ files across the repository.

## 3. Critique of the Plan

### 3.1 Is Making This Easier a Good Idea?

**Yes, emphatically.** In an ecosystem where LLM frontier and mid-tier models update on a 4-to-8 week cadence, high maintenance friction actively harms the project:
- Maintainers defer model upgrades because the PR overhead is disproportionately high for a simple configuration update.
- Partial updates occur (e.g., updating the provider python file for completions, but forgetting to update documentation tables or effort ladder tests).
- Cognitive load is wasted calculating manual ladder rungs and fixing fragile test assertions.

### 3.2 What Are the Risks and Pitfalls of "Updating as Few Files as Possible"?

While the goal is correct, an uncritical pursuit of "fewest files" contains several traps:

#### Trap 1: Conflating Model Catalogs with Size Aliases
It is tempting to say: *"Why not just define size aliases, and automatically infer supported models from whatever appears in `@xsmall` through `@xlarge`?"*
- **Why this fails**: The universe of completable models is much larger than the size alias pools. SASE supports ~15 Codex models, ~18 Antigravity variants, legacy models (`gpt-5.5`), and specialized models (`muse-spark-1.3-contributor`). Users frequently need explicit `%model:codex/gpt-5.3-codex-spark` or `%model:claude-3-5-haiku` for cost-sensitive or legacy tasks.
- If completion is restricted only to models in size aliases, users lose completion for 80% of valid models.
- If every completable model had to be forced into a size alias, the size alias pools would become unwieldy, violating Decision 15's effort ladder constraints.

#### Trap 2: Dynamic / Online Model Discovery Anti-Pattern
Another tempting idea is dynamic auto-discovery: querying `codex models`, provider APIs, or local CLIs at startup.
- **Why this fails in SASE**:
  1. **Zero-Network / Offline Invariant**: SASE agents run in sandboxed, offline, or CI environments without LLM API keys. Startup must never depend on remote HTTP requests.
  2. **Sub-50ms Latency**: The ACE TUI and editor LSP require instantaneous startup and completion keystroke responsiveness (<5ms). Spawning external subprocesses or making network calls during completion breaks the interactive editing experience.
  3. **Model Clutter**: Vendor APIs return hundreds of unusable IDs (embeddings, moderation, deprecated base models). A coding agent requires a curated set of tested models.

#### Trap 3: The "Test Tax" Illusion
If we consolidate `model_alias_defaults.yml` and `codex.py` into a single file, but leave the test suites untouched, **maintainers will still have to edit 10 files per PR**. The pain maintainers feel is not just opening two YAML/Python files; it is spending an hour updating snapshot assertions and parametrized test tables across `tests/`.

## 4. Required Adjustments to the Requirements

To achieve a robust, long-term solution, we must adjust and clarify the project requirements:

1. **Two-Tier Declarative Structure**:
   The manifest must explicitly separate:
   - **Provider Model Catalogs**: The curated list of supported models per provider, their display shorthands, supported reasoning effort levels, and advisories.
   - **Size Alias Routing**: The mapping of `@xsmall`..`@xlarge` to load-balanced pools, fallback chains, and explicit effort levels.
   Both can and should live in the **same file**, but they must remain distinct logical schemas.

2. **Preserve Third-Party Pluggy Architecture**:
   Built-in providers should consume the central declarative file by default, but the underlying pluggy hook specifications (`llm_known_model_names`, `llm_model_short_aliases`) must remain intact. If an external plugin (e.g., `sase-deepseek`) registers via `sase_llm`, the registry must merge its models seamlessly without requiring edits to SASE core's YAML.

3. **Decouple Test Assertions into Property Invariants**:
   Tests asserting shipped defaults must be rewritten as **invariant checks** rather than string-matching checks:
   - *Invariant A*: All alias targets parse into valid selectors.
   - *Invariant B*: All referenced models exist in the known provider catalog.
   - *Invariant C*: Every alias reaches $\ge 2$ distinct providers.
   - *Invariant D*: The effort ladder strictly descends according to Decision 15.
   - Exact behavioral tests (e.g., round-robin rotation order, fallback traversal on error) must strictly run against **frozen synthetic fixtures** (`_model_alias_defaults_fixture.py`).

4. **Automated Documentation Synchronization**:
   The Markdown tables in `docs/llms.md` must not be manually edited. A lightweight generator or validation check in `just check` must ensure documentation is either generated or verified directly against the manifest.

## 5. Architectural Alternatives Considered

### Alternative A: Status Quo with Scaffolding Script
- **Concept**: Keep the current architecture (Python provider lists + `model_alias_defaults.yml`), but write an interactive CLI tool (`sase dev model bump`) to update all 15+ files via AST parsing and regex replacement.
- **Trade-offs**: High maintenance cost for the script itself; fragile regex updates against Markdown and Python files; doesn't fix underlying architectural coupling.
- **Verdict**: Rejected. Treats symptoms rather than the root cause.

### Alternative B: Per-Provider YAML Manifests + Alias YAML
- **Concept**: Split models into `src/sase/llm_provider/<provider>/models.yml` and keep `model_alias_defaults.yml` separate.
- **Trade-offs**: Cleaner separation of provider boundaries, but updating a model and adding it to an alias still requires modifying multiple files across directories (e.g., `codex/models.yml` + `model_alias_defaults.yml`).
- **Verdict**: Rejected. Does not satisfy the user's requirement to update both in the fewest files possible.

### Alternative C: Unified Model & Alias Manifest (`catalog.yml`) [RECOMMENDED]
- **Concept**: Consolidate provider model manifests, short aliases, tier fallbacks, effort capabilities, and size alias pools into a single declarative file: `src/sase/llm_provider/catalog.yml` (or expanded `model_alias_defaults.yml`).
- **Trade-offs**: Centralizes built-in model metadata; provides a single edit point for maintainers; built-in plugins become thin adapters; tests and docs can bind to a single source of truth.
- **Verdict**: **Recommended**. Provides the absolute minimum file edits (1 file for both operations) while preserving clean architectural boundaries.

### 6.2 Provider Plugin Simplification

Built-in provider classes (`CodexProvider`, `ClaudeCodeProvider`, etc.) no longer maintain hardcoded lists of model strings. Instead, they inherit from or delegate to the loaded catalog:

```python
# src/sase/llm_provider/codex.py

class CodexProvider(LLMProvider):
    # Model lists, shorthands, and tiers are loaded from catalog.yml
    _CATALOG_ENTRY = get_builtin_provider_catalog("codex")

    def resolve_model_name(self, model_tier: ModelTier = "large") -> str:
        return self._CATALOG_ENTRY.tiers.get(model_tier, "gpt-6-sol")

    @hookimpl
    def llm_known_model_names(self) -> list[str]:
        return self._CATALOG_ENTRY.known_models

    @hookimpl
    def llm_model_short_aliases(self) -> dict[str, str]:
        return self._CATALOG_ENTRY.short_aliases
```

- **Pluggability preserved**: A third-party plugin that does not exist in `catalog.yml` continues to return its own models via `llm_known_model_names()`.
- **Zero Python edits for new models**: Adding a model to Codex requires zero changes to `codex.py`.

### 6.3 Prompt Input and LSP Completion Integration

The completion pipeline requires **zero architectural changes**:
1. When ACE starts, `sase.xprompt.model_completion` calls `get_llm_metadata_payload()`.
2. The registry queries all provider plugins. The built-in plugins return the models from `catalog.yml`.
3. Size aliases are read directly from `catalog.yml`.
4. `build_static_model_completion_catalog()` constructs `ModelCompletionEntry` objects.
5. In external editors: `xprompt_lsp._materialize_model_catalog()` writes `model_catalog.json`.
6. `sase-xprompt-lsp` reads `model_catalog.json` as it always has. **No Rust code changes or recompilations are needed.**

### 6.4 Decoupling the Test Harness (Solving the "Test Tax")

This is the linchpin of the design. We eliminate fragile literal assertions and replace them with invariant checks:

1. **Property Invariant Tests for Shipped Defaults (`test_shipped_catalog.py`)**:
   Instead of asserting:
   ```python
   # OLD FRAGILE TEST (breaks on every model bump):
   assert "gpt-6-sol" in model_entries
   assert expectations["@large"]["codex/"] == ("codex/gpt-6-sol", "xhigh")
   ```
   We write robust invariant tests:
   ```python
   # NEW INVARIANT TEST (never breaks on valid model bumps):
   def test_shipped_aliases_resolve_to_valid_models():
       catalog = load_llm_catalog()
       for alias_name, alias_spec in catalog.size_aliases.items():
           selector = parse_model_alias_selector(alias_spec.target)
           for member in concatenated_selector_members(selector):
               target, effort = split_model_effort(member)
               provider, model = target.split("/", 1)
               assert model in catalog.providers[provider].models

   def test_shipped_aliases_follow_effort_ladder():
       # Validates Decision 15: scan xlarge -> xsmall, ensure effort drops 1 rung
       # on successive appearances across all models automatically.
       validate_effort_ladder_invariants(load_llm_catalog())

   def test_shipped_aliases_have_multiprovider_redundancy():
       catalog = load_llm_catalog()
       for alias_name, alias_spec in catalog.size_aliases.items():
           providers = get_providers_in_alias(alias_spec.target)
           assert len(providers) >= 2, f"{alias_name} must reach >= 2 providers"
   ```

2. **Frozen Fixture for Mechanics Tests**:
   Tests that verify round-robin rotation, fallback execution, and disabled provider skipping use `tests/_model_alias_defaults_fixture.py`. Because the fixture uses synthetic models (`claude/sonnet`, `codex/gpt-5.5`), updating shipped models in `catalog.yml` never affects mechanical unit tests.

### 6.5 Documentation and Config Drift Prevention

1. **`default_config.yml`**:
   Remove hardcoded model versions from comments. Use stable placeholders:
   ```yaml
   # model_aliases:
   #   builtin:
   #     large: "claude/opus@high | codex/<large-model>@xhigh"
   ```
2. **`docs/llms.md` Auto-Sync**:
   Add a simple Markdown table generator script (`sase dev update-docs` or integrated into `just test-doc-sync`) that automatically updates the "Automatic Provider Resolution" and "Model Short Aliases" Markdown tables from `catalog.yml`. If a maintainer modifies `catalog.yml`, running `just check` will either auto-update the table or flag a clean diff.

## 8. Implementation Roadmap

We recommend executing this transition in four deliberate phases:

```
[ Phase 1: Test Decoupling ]
  - Parameterize test_load_balanced_alias_defaults.py into invariant tests
  - Isolate behavioral tests to _model_alias_defaults_fixture.py
       │
       ▼
[ Phase 2: Catalog Manifest & Loader ]
  - Create src/sase/llm_provider/catalog.yml (schema_version: 2)
  - Implement sase.llm_provider.catalog loader with pydantic/dataclass validation
  - Implement automated Decision 15 effort-ladder validator
       │
       ▼
[ Phase 3: Provider Delegation & Wire Parity ]
  - Refactor built-in LLMProvider subclasses to delegate hooks to catalog loader
  - Verify model_completion_catalog_payload() produces identical wire v1 JSON
  - Verify sase-xprompt-lsp and ACE TUI prompt input completions
       │
       ▼
[ Phase 4: Docs Sync & Deprecation Cleanup ]
  - Deprecate model_alias_defaults.yml in favor of catalog.yml
  - Add doc-sync linting for docs/llms.md
  - Update developer guidance in docs/llms.md
```

### Risk Assessment & Mitigation
- **Risk**: A typo in `catalog.yml` breaks LSP startup in external editors.
  - **Mitigation**: `xprompt_lsp._materialize_model_catalog()` already wraps catalog materialization in a `try...except` block so LSP startup is never blocked. In addition, `catalog.yml` parsing should validate on import with explicit schema errors during `just check`.
- **Risk**: Third-party plugins might break if they relied on internal module structures.
  - **Mitigation**: Pluggy hook specifications remain completely unchanged. Third-party plugins continue to implement `llm_known_model_names()` and `llm_model_short_aliases()` without knowing or caring about `catalog.yml`.

## 9. Conclusion

Updating model alias pools and completion models has historically been painful because configuration, code, tests, and documentation were tightly coupled across dozens of files. 

By unifying provider model manifests and size alias pools into a single declarative `catalog.yml`, having built-in providers delegate their hooks to this catalog, and converting brittle unit tests into invariant verifiers, SASE can achieve the maintainer's goal: **routine model updates will require modifying exactly one file**, with complete safety, full backward compatibility, and zero downtime across the TUI and LSP.
